## 轮 1:对象池——为什么、以及两版实现

### 为什么热路径不能直接 malloc/free

`malloc`/`free` 背后是 glibc 分配器:可能要抢 arena 锁(多线程竞争同一块堆)、可能要向内核要更多页(`brk`/`mmap`,一次系统调用,延迟量级完全不同)、内部按大小分 bin、维护空闲链表,查找/合并的耗时跟当前堆的碎片状态有关。这些都不是"每次都一样多少个 cycle"的操作——它是**数据依赖、状态依赖的变量延迟**。这跟 §1 开篇那句话是同一件事的另一个战场:你要的不是"平均分配很快",而是"每一次分配都同样快,不多一根毛"。

解法是把"跟操作系统要内存"这件事,从热路径里**搬到启动阶段一次性做完**:提前分配好所有以后会用到的内存块,运行时热路径只在这批已经到手的内存里"借用/归还",再也不碰 `malloc`/`free`、不碰内核。这就是内存池(准确说这里是对象池,object pool——池子里放的是同一类型 `T` 的固定数量实例)。

### 朴素版:vector<ObjectBlock> + 线性找空位

```cpp
struct ObjectBlock {
  T object_;
  bool is_free_ = true;
};
std::vector<ObjectBlock> store_;
size_t next_free_index_ = 0;
```

`ObjectBlock` 把一个 `T` 和它的"是否空闲"标记打包在一起,`store_` 是这些块的连续数组。构造函数一次性把 `num_elems` 个块全部预分配好(唯一一次真正找操作系统要内存的地方,发生在热路径开始之前)。

`allocate()`:拿 `store_[next_free_index_]`,placement new 构造对象,标记 `is_free_ = false`,然后调用 `updateNextFreeIndex()` 把指针挪到下一个可用位置,供**下一次**调用用。

`updateNextFreeIndex()` 做的事:从当前位置往后走,遇到 `is_free_` 为 true 的就停,遇到数组末尾就绕回开头——这是一次**线性扫描**。多数情况下(近似先进先出的使用模式)紧挨着的下一格大概率是空的,扫描一两步就停,均摊下来很快。但这只是"通常";如果使用模式比较乱(很多对象长期持有、释放顺序打乱),扫描可能要走很多格才找到空位——**最坏情况是 O(n)**,而且这个"最坏"什么时候发生完全取决于当时的持有/释放模式,不可预测。换句话说:我们把"要不要跟内核打交道"这个变量延迟干掉了,但在池子内部又留了一个新的、量级小得多但性质相同的变量延迟。

### 优化版:显式 free list,永远 O(1)

```cpp
T* objects_;
std::size_t* free_list_;
std::size_t next_free_index_;   // free list 的头
static constexpr std::size_t kInvalidIndex = -1;  // 链表尾
```

思路是把"哪些格子空闲"这件事,从"扫描 is_free_ 标记"换成一条**用数组下标实现的链表**:`free_list_[i]` 存的不是"i 是不是空的",而是"排在 i 后面的下一个空闲格子的下标是几"。`next_free_index_` 就是这条链表的**头**。

- `allocate()`:直接取 `next_free_index_` 当作这次分配的格子,把头挪到 `free_list_[index]`(链表里存好的"下一个")——**不用扫描,一步到位**,永远是同样几条指令。
- `deallocate()`:把刚释放的格子塞回链表**头部**——`free_list_[elem_index] = next_free_index_`(它指向旧的头),然后 `next_free_index_ = elem_index`(它自己变成新的头)。也是常数步骤。

这跟普通链表(`next` 指针散落在堆里、指针一路 cache miss)的关键区别是:这里的"链表"完全铺在一段**连续预分配好的数组**里,下标当指针用——既有链表 O(1) 增删的好处,又不用付"到处跳内存地址"的缓存代价。代价是换了内存管理方式:不再用 `std::vector`(它会自己管生命周期),改用 `std::aligned_alloc` 手动拿一块对齐好的原始内存,所以析构函数要自己找出还没释放的对象手动调用析构、再 `std::free` 底层内存——vector 帮你做的事,现在自己做。

两版的核心差别就一句话:朴素版把"找空位"这件事的耗时变成了**看运气**(通常快,偶尔慢);优化版把它变成了**看不出耗时**(每次都一样,因为压根不用找,链表已经告诉你下一个是谁)。HFT 要的是后者。

**〔补〕** 朴素版里 `ObjectBlock` 把 `T` 和 `is_free_` 放一个结构体、一个 vector,而不是"一个 vector<T> + 一个 vector<bool>"分开存——这是 §5 学过的缓存局部性:一次分配同时要读/写这两个字段,放一起大概率落在同一条缓存行,一次搬运搞定;拆开存的话,两次内存访问可能落在不同缓存行、甚至不同页,平白多一次搬运。

## 附一:轮 1 自检题与你的答案

**Q1:为什么 HFT 热路径要避免直接调用 malloc/free?**(说本质原因,不是"因为慢")
你的答案:glibc 分配器——并发线程数超过 Arena 数量时会抢同一把锁;可能要跟内核要更多页(系统调用);堆碎片与 bin 查找逻辑复杂。
批注:机制列得对且比原讲解更precise(补充了"线程数超过 arena 数量才抢锁"这个准确触发条件)。轻回炉:没收口到"本质原因"——这几条机制的共性是**耗时跟当时堆状态挂钩,是变量不是常数**,HFT 受不了的是"这次分配要多久自己都不知道",不是这些机制本身慢。

**Q2:两版 MemPool 的 allocate() 最坏情况分别是什么?优化版为什么能保证"永远"是 O(1)?**
你的答案:第一版 O(n) 遍历;第二版 O(1),维护 free list,查找和维护操作都是 O(1)。
批注:复杂度类别对。轻回炉:"为什么永远 O(1)"没有真正回答,只是把结论重复了一遍。真正原因:free list 是**每次 alloc/dealloc 顺手维护**的(不是 alloc 时才现找),所以任何一次 allocate() 调用时"下一个空位是谁"早就以数据形式摆在 `next_free_index_` 里,不需要搜索——固定几条指令,跟历史分配/释放顺序无关。

**Q3:free_list_[i] 里存的是什么?这个设计怎么把数组变成链表?**
你的答案:存下一个可用位置;用了侵入式(intrusive)链表。
批注:第一句对。**术语纠正**:这不是侵入式链表——侵入式的准确含义是 next 字段长在 payload(T)内部,对象自己就是节点;这里 `free_list_` 是跟 `objects_` 完全分开的平行数组,T 不知道自己被链进链表,更准确叫法是"**用数组下标实现的空闲链表**"。真正的侵入式做法是用 `union` 把"下一个空闲下标"叠进 T 还没构造时的那块内存(省掉 `free_list_` 这个额外数组)——源码选了"多开数组"这个更简单安全的版本,省内存 vs 好维护是真实权衡。

## 轮 2:内存调优 + TLB Shootdown

池子解决了"热路径不再主动调用 malloc/free",但还有两条口子:内存已到手也可能被换出去;内核在背后做的一些事会连累到你。

**堵"被换出去"**:`mlockall(MCL_CURRENT | MCL_FUTURE)` 锁住现在持有的和以后会拿到的所有页,永不换出;配合 `swapoff -a`/`vm.swappiness=0` 降低内核换出的倾向。实操前提:要 root 或 `CAP_IPC_LOCK`,还要 `ulimit -l` 给够额度,否则直接失败。

**容易漏想的坑:mmap 会悄悄撤销 mlockall。** glibc 对超过 `M_MMAP_THRESHOLD`(默认 128KB)的分配走 `mmap` 而不是堆;`free()` 这类内存时默认会 `munmap()`——而 `munmap` 不是解锁,是把整个映射连同锁定状态一起撤掉。`M_MMAP_MAX=0` 强制所有分配走堆,`free()` 只是内部标记复用、从不 `munmap`,锁定状态才能一直有效。`M_TRIM_THRESHOLD=-1` 是同一思路用在堆自己身上——禁止堆顶空闲攒够后自动收缩归还。`M_ARENA_MAX=1` 是另一维度:放弃 glibc 给每线程分配 arena 的多线程优化(反正分配只发生在启动阶段),换来少一处 mmap 来源。

**TLB Shootdown——绕开调度器、直接打断别的核。** 页表被改动(`munmap`/`mprotect`/THP 合并页)时,内核不知道哪些核缓存了旧翻译,只能给"最近跑过这个地址空间"的所有核广播 IPI(处理器间中断),收到的核必须立刻停下处理、再恢复——微秒级,核越多波及越广。**`isolcpus` 挡不住这个**——isolcpus 管调度层"会不会塞任务给这个核",TLB shootdown 走的是完全不同的硬件中断通道,只要这个核最近跑过你进程的地址空间就会被算进名单,不经过调度器。范围是同一进程的地址空间,不是任意进程,但哪怕热线程独占隔离核、调度层面干干净净,自己进程里别的线程调用 `munmap`/`mprotect`,或 THP 后台合并页,照样能精准打断热核。

**〔补,连回 §4〕** #4 讲关 THP 的理由是"khugepaged 合并耗时不可预测";这里是同一开关的另一层理由——合并动作本身触发 TLB shootdown,连累已隔离好的热核。自动 NUMA balancing(`numa_balancing=0`)同理:搬页提升局部性听着好,但搬页要改页表,对已经手工绑好核/内存的系统是纯负资产。

监控:`watch -n5 -d 'grep TLB /proc/interrupts'`、`perf stat -e tlb:tlb_flush`。

**数据结构选择(顺带)**:避免频繁触发重新分配/拷贝的结构(插删多用 `std::list` 而非 `std::vector`),固定大小短生命周期数据栈上开 `std::array`——跟这一轮同一件事的延伸:能不触发分配器就不触发。

## 附二:轮 2 自检题与你的答案

**Q1:为什么光有 `mlockall` 还不够,一定要配合 `M_MMAP_MAX=0` 和 `M_TRIM_THRESHOLD=-1`?**
你的答案:`mlockall` 告诉内核——现在持有的和以后会拿到的所有页都锁进物理内存,不许换出。`M_MMAP_MAX=0`:单次 malloc 超过门槛(默认 128KB)时 glibc 会绕过堆直接 `mmap`,`free` 时立刻 `munmap` 还给内核。`M_TRIM_THRESHOLD=-1`:只有主 Arena 用 `sbrk`,非主 Arena 内部申请统统走 `mmap`,冷线程在自己 Arena 里申请释放大内存仍会偷偷触发 `munmap`。
批注:`mlockall` 部分对。`M_MMAP_MAX=0` 机制也对(128KB 门槛、`mmap`、`free` 触发 `munmap`),但少了最后一步收口——**为什么"还给内核"就等于"锁没了"**:`munmap` 不是"解锁",是把整个虚拟内存映射连根拔起,这块地址空间对进程而言已经不存在了,`mlockall` 加的锁是映射的一个属性,映射没了锁自然跟着没了。这才是"为什么 `mlockall` 不够"的真正答案,你把机制复述对了,但这句因果没点破——跟轮 1 Q2 是同一个模式(结论/机制对,收口差一步)。

`M_TRIM_THRESHOLD` 这块**串了题**:"非主 Arena 都走 mmap"这个事实本身没错,但它是 `M_ARENA_MAX=1` 要解决的问题(每多开一个 arena 就多一个 mmap 来源),不是 `M_TRIM_THRESHOLD` 管的范围。`M_TRIM_THRESHOLD` 管的是**主 Arena 自己**:free 掉的内存堆在堆顶攒多了,glibc 默认会用 `sbrk` 把这部分收缩还给 OS(叫 trim);设成 `-1` 就是禁止这个收缩,哪怕堆顶空出一大片也不主动归还。道理和 `M_MMAP_MAX` 完全一样(拿到手的页不还回去),只是发生在堆的另一条路径(`sbrk` trim)而不是 `mmap`/`munmap`。

**Q2:TLB shootdown 完整链条是什么——哪个操作触发、内核怎么处理、代价落在谁身上?**
你的答案:触发是 `munmap`/`mprotect`/THP 后台合并页——页表映射被改动后,其他 CPU 上缓存的 TLB 条目可能已经过期;内核不知道具体哪几个核缓存过这份翻译,只好广播 IPI(核心越多、可能需要通知的 CPU 越多、IPI 越多、同步成本越大);收到中断的核必须立刻停下手头的事,跳去内核态把过期 TLB 条目清掉再恢复,微秒级,表现为性能尖刺。
批注:链条完整且对。"核越多→需通知的越多→IPI 越多→同步成本越大"这条推论是你自己补的,原讲解没这么展开,是准确且有价值的延伸。唯一要收紧的是措辞:"内核不知道哪几个核缓存过就全发"单独读容易被理解成"广播给机器上所有核"——但看你 Q3 的答案,你其实很清楚广播范围是"同一进程最近跑过的核"(用 `mm_cpumask` 圈定),所以这只是表达上松了一点,不是理解错了。

**Q3:`isolcpus` 能不能挡住 TLB shootdown 打断你的热核?为什么?**
你的答案:挡不住。`isolcpus` 管的是调度层——会不会主动往这个核上塞任务。TLB shootdown 是物理级硬件中断:只要热核跑过当前进程,它的 CPU 编号就被记入内核的 `mm_cpumask`,一旦同进程的冷线程改了页表,广播就会触发,尖刺照样打过来。
批注:完全正确,而且比原讲解更precise——我当时只说"这个核最近跑过你进程的地址空间就会被算进名单",你直接点出了背后的内核数据结构 `mm_cpumask`。这是这两轮里最扎实的一个答案:结论对、层次分明(调度层 vs 硬件中断层)、机制到位。

**小结**:Q2/Q3 很扎实,`mm_cpumask` 这个点名尤其好。Q1 里 `M_TRIM_THRESHOLD` 和 `M_ARENA_MAX` 的职责混了,记一笔回炉;其余是"机制对、因果收口差一步"的老问题,继续保持自己补充推论的习惯(Q2 那条核数→IPI 数的链就是好例子)。

## 轮 3:pinned_arena + 自定义 STL 分配器

轮 1+2 解决的是"自己的池子"——池子里只装一种类型 `T`,分配/归还走自己写的接口。这一轮要解决:能不能让 `std::vector`、`std::string` 这些 STL 容器本身,一次都不碰全局堆?答案是自定义一个符合 STL allocator 接口的类型,把它背后的存储换成一块自己控制、锁死、预分配好的内存——`PinnedArena` + `LowLatencyAllocator`。

### 1. PinnedArena:一根只会往前走的指针

**直觉**:想象一卷纸带,手里一支笔标着"划到第几个字节了"(起点 0)。有人要 20 字节,笔从 0 挪到 20,把这段给他;下一个要 32 字节,笔从 20 挪到 52。每次分配就是"挪笔 + 返回挪之前的位置",没有别的动作——不用找空位,因为压根没有"空位"这个概念。代价是没法说"把中间那 20~52 字节还给我"——纸带没有"擦掉中间一段"这个操作,想回收只能把笔一次性拉回 0,整卷重来(`reset()`)。

**严谨版**:代码里"一卷纸带"是一个 `MemoryBlock`,核心两个数字:`capacity`(这卷多长,默认 64KB)、`used`(笔划到第几个字节)。`current_block_idx_` 记"现在用第几卷"。`allocate(size)`:把写入位置按对齐要求向上取整(`(ptr+alignment-1) & ~(alignment-1)`,对齐取整的标准位运算),算出这次占用字节数,`used+这次字节数` 没超 `capacity` 就直接挪 `used`、返回旧位置;超了就调 `allocate_slow_path`——先试试当前块换个方式塞不塞得下,不行就激活下一卷(早在构造时就分配好了,这里只是 `is_active` 打开、`used` 清零),全用完了才考虑 malloc 兜底或失败。`reset()` 把每卷 `used` 清零、`current_block_idx_` 拉回 0。

跟轮 1 的权衡:free list 版本要维护"下一个空位是谁"的链表,这里连链表都不需要,一个 `used` 数字就够,比轮 1 还快;代价是没有"归还一小段"这回事(arena 压根没有给每次分配单独记"这段内存从哪到哪"的元数据),只能整卷一起 `reset()`。适合"一批东西一起用、一起扔"的场景(比如一次 tick 处理完的临时数据),不适合寿命参差不齐的对象。`reset()` 只清 `used`、不把内存还给操作系统("保持 mlock 状态")——跟轮 2 的 `M_TRIM_THRESHOLD=-1`/`M_MMAP_MAX=0` 同一句话的另一个战场:内存到手就不还。

### 2. 启动时先把不确定的事情做完:mlock + pre-fault

**直觉**:领到的这卷纸带,严格说只是"预订"——供应商真正把纸印出来,是等笔第一次划到某一段才现印,这一下会卡顿。所以正式开工前,先把笔在整卷纸带上空划一遍,把"现印"这件事在开工前全部逼出来做完;然后把这卷纸用胶水粘死在桌上,不许被收走。

**严谨版**:`initialize_arena_memory()` 只在构造时跑一次(冷路径):`posix_memalign` 按页对齐拿一块连续内存;`mlock(raw_memory, total_size)` 锁进物理内存——注意这不是轮 2 的 `mlockall`,`mlock` 只锁这一段 arena,不是整个进程现在/未来所有的页,两者互补,不冲突;然后 `memset(raw_memory, 0, total_size)`。

memset 这步叫 pre-faulting:Linux 虚拟内存默认惰性——`posix_memalign` 给的只是虚拟地址,背后真正的物理页要等第一次**写**才触发一次缺页中断,内核这时才分配物理页、建立映射,这一步要陷入内核态。memset 提前把整块内存写一遍,相当于在不在乎慢的启动阶段把所有缺页中断吃完,热路径运行时每一页早就映射好了。

这跟轮 1"把跟内核要页这件事挪到启动阶段"、轮 2"锁住不让换出"是同一条主线的第三步——只是**具体机制不同**(malloc 的不确定性来自 arena 锁竞争/堆碎片查找/偶尔的系统调用;缺页中断来自 MMU/分页子系统首次建立映射,两条不同的子系统),但**模式相同**:操作的耗时取决于"是不是第一次/抢不抢得到资源",没法提前算准,应对方式都是把它提前挪到不在乎延迟的启动阶段一次性做完,不留给热路径撞上。

### 3. 主动预取:把 §5 的被动局部性变成一条指令

**直觉**:像服务员看你要坐下了,不等你开口先把水倒上——他知道你两秒后肯定要喝。`allocate()` 把地址交出去的时候,几乎确定调用者下一步就要写,所以提前告诉 CPU"把这块搬进缓存"。

**严谨版**:底层是 `__builtin_prefetch`。§5 讲的是被动局部性(排列数据让它天然落进同一缓存行);这里是主动的、指令级的提前搬运。顺带一提,代码里的 `LIKELY`/`UNLIKELY`/`HOT_PATH`/`COLD_PATH` 是 #12 分支预测的内容,这里先眼熟,#12 讲原理。

### 4. LowLatencyAllocator:接入 STL 的翻译官

**直觉**:`std::vector` 不知道怎么跟你的 arena 直接打交道,它只认识一种固定的问答方式(给我 N 个、把这个收回去、在这建一个对象、把这个销毁)。`LowLatencyAllocator` 是翻译官,把 vector 的问法转成 arena 的问法。

**严谨版**:`allocate()` 转发给 `arena_->allocate()`;`deallocate()` 是空函数(arena 没有"归还一小段");`construct`/`destroy` 是 placement new / 显式析构;`rebind` 是容器内部需要换一种类型分配时用的机制。细节:`make_pinned_vector<std::string>` 只把 vector 内部那段连续数组搬进了 arena,每个 `std::string` 自己如果超出小字符串优化(SSO)缓冲区,还是走默认分配器上堆——demo 里字符串很短,大概率落在 SSO 内,所以问题不会暴露。

---

**〔补〕一个真的坑**(不在源笔记里,是笔者读代码时自己发现的,笔记原文没有任何提示——加进来是因为这个项目一开始定的目标里有"能挑坑",而这个坑正好是"代码看起来很专业(cache line 对齐/mlock/prefetch 一样不少)、demo 也能跑出正确结果,但两处独立的地址计算基于不同的内存布局假设"这类典型问题,面试里被要求 review 内存池/分配器代码时考的就是这种反应)

假设(为了好算,不是真实默认值):header 占 64 字节,每卷正文 1000 字节,一共 4 卷。

初始化时,总内存大小按"header 紧挨自己的正文"算:`(64+1000)×4=4256` 字节——这个数没错,但只是"留多少空间",不代表"怎么摆"。

真正决定"第 i 卷 header 在哪"的是 `arena_mem_.blocks[i]` 这个数组下标——`MemoryBlock*` 类型下标,C++ 规定每挪一步只走 `sizeof(MemoryBlock)`=64 字节,不会跳过 1000 字节正文。所以实际地址是:blocks[0]=0,blocks[1]=64,blocks[2]=128,blocks[3]=192——四个 header 紧挨着排在 [0,256)。

而 `data()` 算的是 `this+1`,也就是"自己的地址+64":block0.data()=64,block1.data()=128,block2.data()=192——分别精确等于 block1、block2、block3 的 header 地址。也就是说,block 0 一旦真写入数据,覆盖的不是自己的正文,而是 **block 1 的 `used`/`capacity`/`is_active`**;block 1 写多了砸 block 2 的 header;以此类推。(最后一卷是边界情况,不细究。)

这个坑在源笔记的 demo 里**不会暴露**:demo 分配的数据量太小,从没触发"这卷用满、切下一卷"的条件,被写坏的 header 从没被真正读取过。跑一次看输出正常,只证明"这次测的这几个输入没撞上坑",不证明代码没问题。

**怎么修**:问题在于 `data()` 每次都临时靠 `this+1` 去猜地址,而不是用已经算好但没人用的 `data_start`。修法是让每块在初始化时就把自己的数据区地址算好、存起来:

```cpp
// MemoryBlock 里加一个字段
char* data_ptr;
char* data() { return data_ptr; }   // 不再临时计算

// initialize_arena_memory 的初始化循环里加一行
for (uint32_t i = 0; i < num_blocks; ++i) {
    MemoryBlock* block = &arena_mem_.blocks[i];
    block->used = 0;
    block->capacity = block_size;
    block->is_active = (i == 0);
    block->data_ptr = arena_mem_.data_start + i * block_size;  // 新增
}
```

## 附四:轮 4 自检题与讨论

**Q1:`std::vector<int>` 和 `std::vector<int, LowLatencyAllocator<int>>` 为什么是两个不兼容的类型?`std::pmr::vector<int>` 怎么绕开这个问题?**
你的答案:C++ 容器的完整类型是 `vector<T, Allocator>`,分配器是类型的一部分,所以两者不同;`polymorphic_allocator<T>` 内部只存一个指向 `memory_resource` 的指针,本身类型不随指向的资源变化,靠运行时多态转发给实际资源。
批注:内容对。前半句贴近讲解原句,后半句"运行时多态转发"是自己的收束。过,提醒平时练习脱稿复述——面试时手边没有原文可以贴近。

**Q2:`monotonic_buffer_resource` 和 `PinnedArena` 共同的限制是什么?**
第一次答案:与讲解原句基本一致(判定为复述,打回重答)。
第二次答案:只用指针的移动往前分配,reset 时指针回到原点,一次性释放。
批注:核心对,这次是自己的话,过。两处收紧:①"析构为空"不准——析构(`~T()`)正常发生(轮 3 的 `construct`/`destroy` 还在起作用),空操作的是 `deallocate`(还内存)这一步,两个动作要分清。②"reset"是类比轮 3 自己推出来的方法名,方向合理但未经核实——标准库对应方法印象中叫 `release()`,语义可能跟 `PinnedArena::reset()` 不完全等价(`release()` 似乎会把运行期间因初始缓冲区不够、额外问上游要的内存真正还回去,只留最初那块缓冲区复用),这部分没有 100% 确认(当时 WebSearch 报错没能核实),需要精确结论请自行查 cppreference。

**Q3:`create_vec()` 里到底是什么"悬空"了?`vec` 本身按值返回,为什么还会出问题?**
你的答案:指向分配器的指针悬空了;返回的是指向原来地址的指针,指向的是一个临时对象,这个对象出了 `{}` 就被销毁了。
批注:方向对,全程是自己的话。两处术语要精确:①不是"有个指针指向分配器",是分配器自己内部持有一个指向 `memory_resource` 的指针,悬空的是这根指针——方向反了。②`resource` 是有名字的局部变量,生命周期到函数结束;C++ 里"临时对象"特指没有名字、只在表达式求值期间存在的对象,不是这种情况,准确说法是"局部对象"。
