## 一、`inline` 其实是两个不相干的东西,共用了一个关键字

**第一个含义,链接期指令,解决 ODR**([源笔记:4](../../trading-system-notes/chinese/01-low-latency/08-内联及内联汇编.md:4))。一个普通(非 `inline`)函数/全局变量,如果定义写在头文件里、被多个 `.cpp` 包含,每个 `.cpp` 独立编译出的目标文件里都会有一份定义,链接器把它们合到一起时会看到好几份同名定义,直接报"重复定义"错误——链接器不知道该留哪一份。`inline` 告诉链接器"这些都是同一份定义,去重就行,最终只留一份"。这就是为什么 class/struct 声明内部直接写出来的成员函数、以及所有模板(函数模板、类模板的成员函数)都是**隐式 `inline`**([源笔记:10](../../trading-system-notes/chinese/01-low-latency/08-内联及内联汇编.md:10))——没有这条规则,几乎所有写在头文件里的 C++ 代码(模板、header-only 的类)根本没法链接通过。C++17 的 `inline` 变量把同一套保证扩展到全局变量,让你能直接在头文件里定义(不只是声明)一个全局唯一实例(如 `inline AppConfig cfg;`),不用再靠"头文件里 `extern` 声明、某一个 `.cpp` 里单独定义"这种老写法。

**第二个含义,编译器的优化建议**([源笔记:15](../../trading-system-notes/chinese/01-low-latency/08-内联及内联汇编.md:15)),跟上面那条完全独立。它只是建议编译器"考虑把这个调用点直接替换成函数体本身,省掉调用开销"(压返回地址、建栈帧、跳转、`ret` 这一整套),编译器完全可以不理——函数太大、太复杂、递归,通常就会拒绝。反过来,`-O2`/`-O3` 或开 LTO 时,编译器也会主动内联大量从没标过 `inline` 的函数,纯粹按自己的成本收益判断来定,`inline` 这个词在高优化级别下对"到底内不内联"的实际影响很小。

这两个含义值得专门点破,因为很容易被当成一回事:第一个是**语言保证的语义**,只要满足条件就一定发生;第二个只是**建议**,编译器可以照单全收也可以完全无视。同一个函数完全可能"因为写在头文件里被多处包含,必须标 `inline`(含义一),但编译器判断函数太大,实际决定不内联(含义二)"——两件事各走各的。

**`always_inline`**([源笔记:21](../../trading-system-notes/chinese/01-low-latency/08-内联及内联汇编.md:21))是真正能覆盖编译器判断、强制内联的属性——用在你已经 profile 过、确定编译器判断错了的场合(比如一个热路径上极小的函数,编译器出于某种原因就是不内联)。**`flatten`**不只内联被标的函数本身,还尽量把它内部调用到的函数也一并递归内联进来(前提是那些函数本身可内联),用在小而热的整条调用链(源笔记举例风控快路径、撮合前置校验),代价是代码体积和 i-cache 压力上升,需要 `perf` 实测验证收益;两者不是同一个方向——`always_inline` 是"强推某一个调用点",`flatten` 是"尽量摊平整条调用层级"。这条不是标准 C++,GCC/Clang 扩展。

**错误处理内联的 i-cache 陷阱**([源笔记:34](../../trading-system-notes/chinese/01-low-latency/08-内联及内联汇编.md:34)):把错误处理函数内联进热路径,哪怕这条错误分支几乎从不触发,它的指令字节照样占了热路径函数体内的 i-cache 行——i-cache 是按地址/cache line 组织的,不区分"这段代码多久跑一次",错误处理代码混在热代码中间,会把真正天天跑的热指令从 i-cache 里挤出去,提高热路径本身的 i-cache miss 率。这跟 §5 讲的数据 cache 局部性是同一个道理,只是这里的"数据"换成了指令。

## 二、内联汇编——只在 C++ 表达不了的地方亲手写

内联汇编([源笔记:44](../../trading-system-notes/chinese/01-low-latency/08-内联及内联汇编.md:44))是把汇编指令直接嵌进 C++ 文件,靠 `asm`/`__asm__` 之类的关键字标记,好处是不用单开一个 `.s` 文件、能直接读写 C++ 变量,代价是不同编译器的语法差异巨大(MASM/Intel 风格 vs GNU 风格,不是同一门语言),而且编译器没法跨内联汇编块做优化(常量传播、寄存器分配这些在汇编块边界就断了),MSVC 64 位甚至完全不支持内联汇编。

**MASM 风格**(微软/Intel 编译器):`__asm { ... }` 包一段指令,直接写 C++ 变量名、编译器自动换算内存地址,自动保存被改动的寄存器,但不能碰 `ebp`/`ebx` 这类编译器保留寄存器。只在 Windows/32 位场景有意义,64 位 MSVC 完全用不了。

**GNU 风格**(GCC/Clang/Intel Linux)才是 HFT infra 上真正用得到的:

```
__asm__ (
    "汇编指令\n"
    : "输出约束"(变量)   // 如 "=t"(y):栈顶st(0) → y
    : "输入约束"(变量)   // 如 "m"(x) 内存操作数、"a"(n) 强制放进 eax
    : "被修改寄存器"      // 如 "%edx",没声明的话编译器会假设这个寄存器没变
);
```

这四段冒号分隔的结构值得记住形状,不用记语法细节。**局部标签**(`1:`、`9:`,跳转写 `1b`/`9f`)存在的原因是同一段内联汇编可能被内联进多个调用点——普通数字标签在多处展开时会撞名,`1f`/`1b` 靠"往前找/往后找最近的 `1:`"这种相对方式来避免冲突,不需要全局唯一的名字。

**VEX 与非 VEX 混用的坑**([源笔记:187](../../trading-system-notes/chinese/01-low-latency/08-内联及内联汇编.md:187)):同一段热代码里混用 AVX(VEX 编码,如 `vaddps`)和传统 SSE(非 VEX,如 `addps`)指令,会逼 CPU 做一次内部状态切换(YMM 寄存器高 128 位要显式保存/恢复),代价约 70 个 cycle——手写了一段 AVX 又调用一个还在用 SSE 的库函数,很容易不知不觉踩上这个税。修法是跨越前执行 `vzeroupper`,或者干脆让同一个热区始终用同一套指令集。

**手写汇编技巧表**([源笔记:196](../../trading-system-notes/chinese/01-low-latency/08-内联及内联汇编.md:196))源笔记自己定位成参考资料(细节见 Agner Fog manual),不需要背,挑一条已经学过的对上就够:表里"用 `xor reg,reg` 打破伪依赖"这一条,跟 §5 轮 5 `popcnt` 那道伪依赖坑是同一个机制——`popcnt` 的目的寄存器会被 CPU 当成一个"假的"输入依赖(尽管指令本身不读它),必须等这个寄存器上一次写入完成才能执行;紧挨着插一条 `xor dst,dst`,CPU 能识别出这是"清零"这个特殊写法,直接判定不存在依赖,把这条假边砍掉。这张表不是一堆孤立技巧,而是依赖链、对齐、前端吞吐这几个反复出现的原理,在指令选择这个更细粒度上的具体呈现。
