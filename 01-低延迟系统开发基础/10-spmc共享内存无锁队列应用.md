## 轮 1:SPMC 广播环

### 要解决什么:一个生产者,多个下游,每个下游都要收到每一条

场景是交易所的 Level2 行情:一个回调线程不停收到逐笔成交、逐笔委托;下游有好几个——落盘、转发 MQTT、做分析——**每一个都要看到每一条**。

这和 [#9](09-lock-free-queue及micro-batching.md) 的 SPSC 队列是两种不同的问题:

- **#9(SPSC)**:一条消息交给**一个**消费者,取走就没了;生产者要看消费者的读下标才知道队列满没满,满了就得丢或者等。
- **这里(SPMC)**:一条消息要被**每个**读者各看一遍,读者之间互不相干——这是"广播",不是"分活"。
- **硬约束**:生产者是行情热路径,**不能等任何一个读者**。

后面的每个设计选择,都是从这条约束推出来的。

### 数据结构:一圈带"戳"的块

整个类只有 50 行([源笔记:10](../../trading-system-notes/chinese/01-low-latency/10-spmc共享内存无锁队列应用.md:10))。骨架是:

```cpp
template<class T, uint32_t CNT>            // CNT 必须是 2 的幂(static_assert)
class SPMCQueue {
    struct alignas(64) Block {
        uint32_t idx = 0;                  // 这一块里的消息是第几条:"序号戳"
        T        data;                     // 消息本体
    } blks[CNT];                           // 一圈 CNT 个块
    alignas(128) uint32_t write_idx = 0;   // 已经写到第几条
};
```

- **序号戳 `idx`** 是整套设计的关键:每一块自己记着"我里面装的是第几条消息"。发布信号不再是一个所有人共享的下标,而是**每块自带**——这一点决定了后面全部的行为。
- `write_idx` 是普通的 `uint32_t`,不是原子量:只有生产者写它(`getReader()` 建读者时会读它一次)。
- `CNT` 是 2 的幂,所以 `x % CNT` 会编译成按位与(#9 的掩码)。
- 序号是 **32 位**,写满 2^32 ≈ 42.9 亿条之后会回绕到 0。后面比较序号的写法,就是为这件事准备的。

把源笔记里的类和结构体原样编译,得到(x86-64):

| 量 | 值 |
|---|---|
| `sizeof(Lev2Trans)` / `sizeof(Lev2Order)` | 88 B / 80 B |
| `Block` | 128 B:4 B 戳 + 4 B 对齐空隙 + 88 B 数据 = 96 B,`alignas(64)` 再补到 64 的倍数 → 128 B(两个缓存行) |
| 一个队列(`CAPACITY = 524288`) | 67,108,992 B ≈ 64 MiB(= 524,288 × 128,再加 `write_idx` 占的 128 B) |

两处 `alignas` 的用意:块对齐到 64,是让相邻的块不共用缓存行(生产者在写第 i 块时,读者在看别的块,不该因为同一条缓存行互相拽——§5 的伪共享)。`write_idx` 对齐到 128,我的理解是:很多 Intel CPU 会把相邻两条 64 B 缓存行成对预取,要隔离就得按 128 B 算——源笔记没解释为什么是 128,这是我的推断,没有核实。

### 生产者:填数据,最后盖戳

[源笔记:43](../../trading-system-notes/chinese/01-low-latency/10-spmc共享内存无锁队列应用.md:43):

```cpp
template<typename Writer>
void write(Writer writer) {
    auto& blk = blks[++write_idx % CNT];
    writer(blk.data);                                                 // ① 调用者的 lambda 直接往块里填
    ((std::atomic<uint32_t>*)&blk.idx)->store(write_idx, release);   // ② 最后给这一块盖上新序号
}
```

- 跟 #9 的"两步交接"是同一个想法:**先在最终位置原地写,再发布**。区别只是发布动作从"推进一个共享下标"变成了"给这一块盖戳"。
- 生产者**从不读任何读者的状态**。没有"满了"这回事:写满一圈之后,直接覆盖最老的那一块。所以它永远不用等——步数固定,跟读者快慢无关。

### 读者:私有游标 + 三种情形

[源笔记:15-34](../../trading-system-notes/chinese/01-low-latency/10-spmc共享内存无锁队列应用.md:15):

```cpp
struct Reader {                                            // 摘自源码,略去 readLast / operator bool
    SPMCQueue* q;  uint32_t next_idx;                      // 这个对象在读者自己的内存里,不在共享内存里
    T* read() {
        auto& blk = q->blks[next_idx % CNT];
        uint32_t new_idx = ((std::atomic<uint32_t>*)&blk.idx)->load(acquire);
        if (int(new_idx - next_idx) < 0) return nullptr;    // 没有新消息
        next_idx = new_idx + 1;
        return &blk.data;
    }
};
```

**游标是每个读者私有的**:`Reader` 对象放在读者自己的内存里,里面只有一个指向队列的指针和 `next_idx`。读者对共享内存只**读**、从不写。所以:读者之间没有任何竞争;多一个或少一个读者,生产者那条路径一步都不变。(读者越多,生产者写一块时要让越多核缓存里的副本失效——这笔账记在生产者头上,只是它不"等"谁。代价有多大,附一里量了。)

`read()` 拿着 `next_idx`("我想要第几条")去看对应那一块的戳 `new_idx`,按差值分三种情形:

| `int(new_idx - next_idx)` | 意思 | `read()` 做什么 |
|---|---|---|
| **< 0** | 这一块里还是上一圈的旧数据:生产者还没写到我要的那一条 | 返回 `nullptr`——没有新消息 |
| **== 0** | 正好是我在等的那一条 | 返回数据,`next_idx = new_idx + 1` |
| **> 0** | 生产者已经绕过了一圈以上,这一块已被**更新**的消息覆盖——读者被"套圈" | 照样返回这块里现在的数据,`next_idx = new_idx + 1`:**中间的消息直接跳过了** |

跑一遍(`CNT = 8`,读者还没读,生产者已经写了 20 条):读者依次拿到 **17、18、19、20**——第 1~16 条从没送到,而且**队列不会告诉读者它丢了**(`read()` 只返回指针,不报差值)。要发现丢消息,得靠消息里自带的连续序号,或者改 `read()` 把差值报出来。

**为什么写成 `int(new_idx - next_idx)`,而不是 `new_idx < next_idx`?** 因为序号是 32 位会回绕。把差值转成有符号数,只要两者相差不到 2^31,回绕前后大小关系都是对的;直接比较在回绕点会判反。实测:`next_idx = 0xFFFFFFFE`,回绕后新序号 `1`,有符号差值是 +3(新消息,对);直接比较 `1 < 0xFFFFFFFE` 为真(错判成"还没写")。

另外两个入口:

- **`getReader()`**([源笔记:36](../../trading-system-notes/chinese/01-low-latency/10-spmc共享内存无锁队列应用.md:36)):`next_idx = write_idx + 1`,从"下一条"开始读,**不回放历史**。实测:写了 5 条之后才建的读者,第一次 `read()` 是 `nullptr`,下一次写入之后读到第 6 条。
- **`readLast()`**([源笔记:26](../../trading-system-notes/chinese/01-low-latency/10-spmc共享内存无锁队列应用.md:26)):一直 `read()` 到没有为止,只留最后一条。适合"我只要最新一份快照"的读者。实测:写 5 条后返回第 5 条。

### 内存序:戳就是发布信号

- 生产者:先填数据(普通写),再对 `idx` 做 **release** 存储;
- 读者:先对 `idx` 做 **acquire** 读取,再读数据。

这就是 #9 的 release/acquire 配对(§5 轮 3)原样搬过来:读者一旦通过 acquire 看到了新戳,就一定能看到这条消息的数据已经写完。区别在于:#9 里发布信号是一个**共享的写下标**,这里是**每块自带的戳**,所以任意多个读者都可以各自独立地判断"这一块我现在能不能读",不需要读者之间、也不需要读者和生产者之间共享任何可写状态。

### 这个设计不保证什么

到这里可以看出这个设计的核心交换:**生产者不等任何人,换来的是读者得自己扛后果。**

**(a) 没有背压,慢读者会被套圈,而且是默默丢。** 上面已经演示过。真实部署里 `CNT = 524,288`,读者得落后 50 多万条才会被套圈,但读者每条处理得越慢(源笔记里的读者是同步发 MQTT / 写 CSV),越靠近这条边界。

**(b) 读者拿到的是指向共享块的指针,读的过程中块可能被重写——撕裂读。** `read()` 返回 `&blk.data` 之后,读者再逐个字段去读。如果这时生产者恰好绕回来重写这一块,读到的就是新旧混合的数据。下面是压力测试(`CNT = 4`,生产者全速写,每组 3 秒——故意最恶劣的设置,只为证明这件事会发生):

| 情形 | 被接受的读取 | 其中撕裂 |
|---|---|---|
| 源码原样:拿到指针就读 | 59,869,704 | 3,269,273(约 5.5%) |
| 读完数据后,**再读一次 `idx`**,变了就丢 | 43,942,557(另有 8,861,343 次被丢弃) | 2,084,572(约 4.7%) |
| 生产者改成"**先作废戳、再写数据、最后盖新戳**",读者读完再检查 | 38,607,078(另有 6,436,383 次被丢弃重读) | **0** |

第二行是重点:"读完再检查一次戳"这个直觉修法**防不住**。原因是这个生产者**先写数据、最后才改戳**——重写进行到一半的时候,戳还是旧的,读者重检看到"没变",于是放行了一份写了一半的数据。只有生产者先把戳作废,读者的重检才抓得到"正在被重写":

```cpp
// 生产者:改成三步
((std::atomic<uint32_t>*)&blk.idx)->store(0, relaxed);            // ① 先作废戳
std::atomic_thread_fence(release);
writer(blk.data);                                                  // ② 再写数据
((std::atomic<uint32_t>*)&blk.idx)->store(write_idx, release);    // ③ 最后盖新戳
// 读者:复制完数据 → atomic_thread_fence(acquire) → 再读一次 idx;不等于刚才那个序号就丢弃这份拷贝
```

(在 x86 上测的;严格按 C++ 内存模型,数据字段本身也要是原子的,这里不展开。)

这些是压力测试划出的边界,不是说源码在真实部署里天天出错——它靠"队列够大 + 读者够快"把概率压到很低,但没有把它压到零。

### 小结:三句话

1. 这是**广播环**:每块自带序号戳,读者各持私有游标,生产者从不等读者。
2. `int(new_idx - next_idx)` 的三种符号 = 没新消息 / 正好 / 被套圈,而且回绕安全。
3. 代价由读者承担:会默默丢消息,慢读者还可能读到撕裂的数据。

## 附一:轮 1 自检题与你的答案

**Q1:#9 的 SPSC 队列里,生产者每次写之前要读消费者的 `read_idx`;这里的 SPMC 生产者一次都不读读者的状态。为什么这里可以不读?这样换来了什么,又付出了什么?**
你的答案:采用了覆盖式,生产者拥有绝对的写权限;换来了缓存行隔离,生产者只涉及自己的 L1 cache,读者的增加不会影响生产者的速度;付出了被套圈、撕裂的代价。
批注:**取舍的两头都点对了;其中"读者增加不会影响生产者速度"要收紧——这正是我在正文里留了"没有量化"的那笔账,这次量了。**

- **对的部分**:
  - "覆盖式"是根因:这个队列根本没有"满了"这个状态,写满一圈直接盖掉最老的块,所以生产者不需要知道任何读者读到了哪。
  - 换来的(你说的"生产者拥有绝对的写权限"):生产者**不等人**,执行路径与读者无关——没有等待、没有重试、没有循环;读者只读不写、游标各自私有,所以也没有 #9 那种"大家轮流抢着写的共享游标"。
  - 付出的:套圈丢消息 + 撕裂读,就是正文"不保证什么"的 (a)(b)。
- **要收紧的一处**:"只涉及自己的 L1 / 读者增加不影响速度"。对的部分是**不阻塞**;"不影响速度"实测不成立。生产者全速写、读者忙轮询(源码里的读者就是 `while (1) { read(); … }`),读者一加,生产者每条就变贵:

| 生产者每条 `write()` 的耗时(ns) | 0 个读者 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|
| 512 KiB 的环(放得进 L2),读者只轮询 | 2.8 | 18.5 | 24.0 | 25.3 | 26.4 | 28.0 |
| 512 KiB 的环,读者还读载荷 | 2.8 | 22.8 | 25.8 | 28.5 | 32.5 | 37.0 |
| 64 MiB 的环(源码的真实容量),读者只轮询 | 12.6 | 15.3 | 17.4 | 19.9 | 22.5 | 26.0 |
| 64 MiB 的环,读者还读载荷 | 12.6 | 20.1 | 26.8 | 29.8 | 33.8 | 38.7 |

  (每格是 3 次运行的中位数,每次 1 秒;AMD Ryzen 5 5600GT(6 核 12 线程)、Windows,生产者钉在 CPU 0、读者钉在不同的物理核;程序:[10-spmc-producer-vs-readers-check.cpp](10-spmc-producer-vs-readers-check.cpp)。)

  - **第一个读者最贵**:放得进 L2 的环里,生产者原本是自己独占、连着写(2.8 ns),一个读者来轮询,就变成 18.5 ns;之后每多一个读者再多约 1~5 ns。
  - **生产者慢下来时几乎看不出**:每 2 µs 写一条时,`write()` 这个调用本身的中位数在 0~5 个读者下都是 10 ns(计时分辨率约 10 ns),变的只是尾部——p99.9 从 20 ns 涨到 70 ns。
  - **怎么读这组数**:读者数不改变生产者的**步数**(没有等待),改变的是每一步的**硬件代价**。读者只读,但它轮询、读过的缓存行会以只读副本留在读者那个核的缓存里;生产者写这一块之前,得先让这些副本作废。生产者的写先进 store buffer(§5 轮 1 的"小本子"),节奏慢时小本子吸得下,全速时排不过来,才体现成吞吐下降。"只读副本—作废—升级"这套机制,留给 MESI 补课系统讲;这里先记结论和数字。
  - 所以更准确的说法是:**读者增加不会让生产者等,但不是免费的。**

**Q2:`read()` 里 `int(new_idx - next_idx)` 的三种情形分别是什么意思?如果差值是 +5,读者接下来会拿到什么?它自己知道丢了消息吗?**
你的答案:`diff == 0`(刚好跟上):读者进度与生产者完全同步,`next_idx` 对应的槽位数据刚刚被生产者发布,可以安全读取。`diff < 0`(读快了/队列无新数据):读者的期待序号超过了生产者已发布的序号(例如生产者还在写,或者还没写到这一条),说明目前没有新消息,读者需要重试或休眠。`diff > 0`:生产者已经绕过一圈,块被更新的消息覆盖,读者被"套圈"。"+5 表示你现在要拿的 x 被覆盖了,并且你拿到了 x+5;我觉得是可以知道的,因为这个 diff>0 就可以说明是丢了。"
批注:**对。三种情形和"+5 拿到 x+5、x 被覆盖"都准确;补四处精确化。**

- **`== 0` 的措辞**:它的意思是"这一块里装的正好是我要的那一条",不是"跟生产者完全同步/刚刚发布"。读者可以落后生产者最新的一条好几条(只要不到一圈),照样是 0;`== 0` 只看这一块。
- **"可以安全读取"的边界**:成立到生产者绕回来重写这一块之前;这正是你 Q3 答的撕裂读——`== 0` 只保证"我读的时候这条已经发布了",不保证"我读完之前不会被重写"。
- **"+5"只是我借来举例的数,真实差值不会是 5**:块里的戳是 `write_idx`,块的位置是 `write_idx % CNT`,所以同一块里的戳永远和槽位同余;读者去看的那一块,戳只可能是 `next_idx`、`next_idx ± CNT`、`± 2·CNT`……差值一定是 CNT 的整数倍(`CNT = 8` 时是 8、16、24;生产环境是 524,288 的倍数)。实测:读者存着 `next_idx = 6`,队列已写到 30,`read()` 返回的第一条是 30,差值 24 = 3×8。
- **"它自己知道吗"**:你的判断有道理——`diff > 0` 本来就是"丢了"的证据,而且跳过的条数正好等于差值,信息在 `read()` 里是现成的。区别只在源码**没把它交出来**:`read()` 只返回指针,`next_idx` 被直接改写,**调用方**从返回值里看不出来。要知道,得让 `read()` 把差值报出来,或在 `Reader` 里累加 `skipped += diff`,一行的事。(顺带一个实测的细节:读者被套圈后,落在哪一块就从哪一块的戳往后读,**不会回头**补还留在环里的更老的消息,见轮 2 第 4 节。)

**Q3:读者拿到数据后,再读一次这一块的 `idx`,发现和刚才一样,能不能断定刚才读到的数据是完整的?为什么?**
你的答案:不能,因为写完数据才盖新戳,写的过程中可能被读撕裂了,然后才盖新的戳。
批注:**对,而且抓在点子上。**生产者重写一块时,戳要等数据写完才变——重写进行到一半的时候戳还是旧的,读者"读完再看一眼"看到没变,就把写了一半的数据放行了。这正是正文表里第二行(仍有约 4.7% 撕裂)的原因。我追一个问题,放进轮 2 的检验题第 1 题。

〔补〕**你追问的:环大到装不进缓存时,生产者写之前是不是基本就是 I?I→M 和 S→M 谁更贵?**(2026-09-24;没有新跑实验,下面标了哪些是实测、哪些是推断)

- **是 I,这个直觉对。** 64 MiB 的环远大于 L2(512 KiB)和 L3(16 MiB),生产者绕回来时这一块早被踢出它自己的缓存了(被踢时是脏的,会先写回内存)。这时的写是**写未命中**:发一次 RFO,把整行取回来并拿到独占,写完是 M。0 个读者时 2.8 ns(512 KiB 环)→ 12.6 ns(64 MiB 环)这个台阶,是"每条要从内存拉两条缓存行、还要写回被踢出的脏行"的**数据搬运**成本,跟有没有读者无关。(与实测台阶一致;没有分层验证。)
- **写未命中没有"先 E 再 M"这一步要付钱。** 有的资料把它画成 I→E→M,是把"拿到独占"和"改写"拆成两步;E→M 本身是静默的,不花钱。E 作为一个**停留的状态**,是读未命中且无人持有时才有。
- **I→M 和 S→M 没有固定的高低**,代价由两件事决定:① 数据要不要从别处搬、从哪一层搬;② 要不要和别的核对话(让对方作废副本、等确认)。
  - **S→M(升级)**:数据本地已有,不搬;但要让别的持有者作废并等确认——一次**跨核往返**。
  - **I→M(写未命中)**:要把行取回来,代价取决于它在哪(L2 几 ns、L3 十几 ns、别的核的缓存几十 ns、内存上百 ns);如果别的核也持有,还得作废它们。
  - 单次孤立访问的通常量级:内存 > 跨核往返 > L2/L3(架构常识,**没在本机测**)。
  - **吞吐上不同**:连续流式写时,预取加多个未完成的请求能把内存延迟叠起来,每条平均反而便宜;而"每条都要一次跨核往返"的 S→M 很难叠。我们那组数里正好有这个对比(**实测**,配置不同、按我的解读):64 MiB 环、0 读者(基本是 I→M 从内存取)12.6 ns/条;512 KiB 环、1 个读者(基本是 S→M 作废读者的副本)18.5 ns/条,后者更贵。
  - 所以别把"I→M 一定比 S→M 贵"当结论记;更稳的口径是:**代价 = 取数据的那一层 + 是否要跨核确认。** 你记的"S→M 代价高"对的部分是:它一定要跨核对话,比 E→M(免费)、比从 L2/L3 取数据都贵;不对的部分是把它排在 I→M 后面或前面当成固定顺序。
- **我上面"怎么读这组数"里的解读要收窄**:"读者的只读副本留在它们的缓存里、生产者写之前先作废"是对**小环、读者紧跟生产者**时的解读(读者一直在轮询生产者马上要写的那一块)。大环里读者上一圈留下的副本早被它自己的缓存淘汰了,那里多出来的代价更可能是读者把生产者刚写好的行拉走(缓存到缓存的转发)——这一句是推断,没验证。

## 轮 2:放进共享内存 —— 跨进程落地与应用层的坑

> 本机是 Windows,没有 `shm_open` / `mmap`。下面凡是"跨进程"的实测,用的是 Windows 上同一件事的对应物(`CreateFileMapping` + `MapViewOfFile`:两个进程按同一个名字映射同一块内存);POSIX 的四个调用只按 API 语义讲,没有在本机跑。代码见本节末。

### 1. `shmmap`:四个调用,把"一个对象"变成"两个进程共用的内存"

[源笔记:62-80](../../trading-system-notes/chinese/01-low-latency/10-spmc共享内存无锁队列应用.md:62):

```cpp
int fd = shm_open(filename, O_CREAT | O_RDWR, 0666);                          // ① 按名字打开(没有就创建)一个共享内存对象
ftruncate(fd, sizeof(Q));                                                      // ② 把它设成队列那么大
Q* ret = (Q*)mmap(0, sizeof(Q), PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);    // ③ 映射进本进程的地址空间
close(fd);                                                                     // ④ 描述符不用了,映射不受影响
```

- **名字相同 = 同一块**:Linux 上这个对象在 `/dev/shm/` 下,是内存文件系统(tmpfs),不落盘。写者和所有读者都调用同一个 `shmmap`、传同一个名字。
- **`MAP_SHARED`**:一个进程对这块内存的写,别的进程也看得到(背后是同一批物理页;#9 的 `memfd` 双映射用的也是 `MAP_SHARED`)。
- **对象比进程活得久**:所有进程都退出了它还在,直到 `shm_unlink` 或重启。
- **没有构造函数**:没人给 `SPMCQueue` 调构造——`mmap` 拿到的只是一块被当成 `Q` 来看的字节。队列靠"**新建对象全是 0**"当空队列(`idx = 0`、`write_idx = 0`),`ftruncate` 扩出来的部分按定义就是全 0。所以这套写法**依赖零初始化**。
- **谁先起谁创建**:写者和读者都带 `O_CREAT`,读者先起就先拿到一个空队列。读者启动顺序无所谓;但要收全数据的读者得赶在写者开始写之前起来(`getReader()` 从下一条开始,轮 1)。

### 2. 同一块内存,在两个进程里地址不同

这是这一轮最要紧的一点。把队列放进 `CreateFileMapping` 的命名映射里,起两个进程,一个写、一个读([10-spmc-shm-demo.cpp](10-spmc-shm-demo.cpp);块里故意放了两个指针):

```
[producer pid 45016] view at 0000017987cc0000
[reader   pid 43260] view at 000001ae3be70000
[reader] got seq=1 ... | m->self=0000017987cc0048 vs my address of this block=000001ae3be70048 (DIFFERENT)
                       | m->lit =00007ff75435b209 vs my own "AAPL"=00007ff75435b209 (same)
[reader] received 3 of 3 messages across the process boundary
```

三件事:

1. **队列跨进程真的能用**:3 条全部收到。
2. **同一块物理内存,两个进程各映射在各自挑的地址上**(`0x17987cc0000` 对 `0x1ae3be70000`)。所以块里存的"指向共享内存自己的指针"(`m->self`:写者眼里这一块的地址)到了读者那里是**错的**。
3. **指向字面量的指针(`m->lit`)这次"碰巧"是对的**:两个进程是同一个 exe,程序映像加载在同一个地址。但这是巧合:写者和读者常常不是同一个程序(源笔记里写行情的回调进程,和转发 MQTT、落盘 CSV 的读者进程就是不同的程序),或者被地址随机化(ASLR)重定位——那时就对不上。**不能依赖。**(这更正了我在 #9 附三〔接回 #10〕里写的"连字面量的地址通常也不能用":准确的说法是"不能依赖",不是"一定不同"。)

结论:**共享内存里的元素必须自包含**——整数、浮点、定长数组;不能含任何指针:指向共享内存自己的不行,指向堆的不行,指向字面量的不能依赖,虚函数表指针也不行。这就是 `Lev2Trans` 的 `SecurityID` 写成 `char[31]`、不写 `std::string` 的原因。

而且 `std::string` 不行得比"长串里有堆指针"更彻底。实测(同一个程序里):libstdc++ 的**短字符串**,`data()` 指向**字符串对象自己内部**的缓冲(`&s` = `…880`,`s.data()` = `…890`)——它存着一个指向自己的指针,搬到另一个进程的地址上就指错了;长字符串的 `data()` 指向堆(`…7c200`)。

(接回 #9 附三 Q3:那里的判据是"被指的东西要活得比读取者久、而且不变";跨进程再加一条——**地址在对方进程里得指到同一个地方**。)

同一个道理还带出三条双方必须一致的"合同":

- **结构体布局**:两个进程用同一份 `Lev2Trans` 定义、同样的编译选项(`sizeof`、偏移、填充都得一样)。改了结构体,旧的共享内存对象就和新程序对不上——要换名字,或者启动时先 `shm_unlink`。
- **一个队列只能有一个写者**:`write_idx` 是普通的 `++`,两个写者会互相踩;源码里每个行情源单独一个队列(`q_trade_sz` / `q_order_sz` / `q_trade_sh` / `q_order_sh`,[:114-117](../../trading-system-notes/chinese/01-low-latency/10-spmc共享内存无锁队列应用.md:114)),各由一个回调线程写。
- **`alignas` 在共享内存里照样有效**,因为 `mmap` 返回的地址是页对齐的(4096 的倍数),队列对象正好放在开头。

### 3. 行情怎么流:一个写者,四个队列,多个读者进程

```
交易所 API 回调线程 ──write──▶ 共享内存队列(每个 ≈ 64 MiB) ──read──▶ 读者进程 A:转发 MQTT
  (OnRtnNGTSTick)                                            └──read──▶ 读者进程 B:写 CSV
```

- **写者**([:120-137](../../trading-system-notes/chinese/01-low-latency/10-spmc共享内存无锁队列应用.md:120)):回调 `OnRtnNGTSTick` 里,`write()` 的 lambda 把交易所结构体的字段**一个一个**拷进块里(`strcpy` 拷代码、`TickTime * 10` 换成 `TradeTime` 等)。
- **读者**([:140-171](../../trading-system-notes/chinese/01-low-latency/10-spmc共享内存无锁队列应用.md:140)、[:174-207](../../trading-system-notes/chinese/01-low-latency/10-spmc共享内存无锁队列应用.md:174)):各自 `shmmap` + `getReader()`,然后 `while (1) { read(); … }`——忙轮询。每个读者一个进程,各有各的私有游标,互不影响;重启一个不会碰到别的。
- 四个队列各 64 MiB(逐笔委托的块也是 128 B),共约 256 MiB 共享内存。

### 4. 应用层的三个坑

**坑 1:第一圈会缺页。** 共享内存对象是"按需分配"的:某个 4 KiB 页第一次被碰到,内核才给它分配一页零页(缺页)。一个块 128 B,**每写 32 条就踩进一个新页**(4096 ÷ 128)。实测(Windows 的命名映射,64 MiB,`10-spmc-shm-demo firstlap`;Linux 上 tmpfs 的机制同类,数字不同):

| | 第 1 圈:平均 / p99 | 第 2 圈:平均 / p99 |
|---|---|---|
| 新映射,不预热 | 56.1 ns / 1,302 ns | 8.6 ns / 10 ns |
| 开写前先对每个 4 KiB 页写一个字节(预热) | 9.0 ns / 10 ns | 8.8 ns / 10 ns |

(计时分辨率约 10 ns。)每次缺页约 1.5 µs((56.1 − 9.0)× 32)。开盘前预热一遍,第一圈就跟第二圈一样;这跟 #6 内存池"第一次不要发生在热路径上"是同一条规矩。

**坑 2:读者慢了会被套圈;余量 = 容量 ÷ 速率差。** 源码里读者是:每条 `fmt::format` 拼一个 `std::string`(一次堆分配),再同步 `mqtt publish` 或 `fprintf`。只要读者每条的处理时间大于生产者每条的间隔,它就在一点点落后;落后满 `CAPACITY = 524,288` 条就被套圈、默默丢(轮 1)。余量的算法很朴素:**能撑的秒数 = 524,288 ÷ (生产速率 − 处理速率)**;读者完全卡住时就是 524,288 ÷ 生产速率——比如每秒 10 万条(举个数),只能撑约 5 秒。所以读者的 `read()` 循环里别做慢事(慢的转给别的队列/线程),并且**监控落后了多少**(写者的 `write_idx` 减读者的 `next_idx`)。

**坑 3:读者重启会丢,除非存游标。** 实测([10-spmc-resume-check.cpp](10-spmc-resume-check.cpp),`CNT = 8`):

```
reader A 读到 1 2 3 4 5 后"崩溃"(存下 next_idx = 6),生产者继续写 6..9,再写 10
  用 getReader() 重建            -> 10            (6~9 没了:getReader 是"从下一条开始")
  用存下的 next_idx 续读         -> 6 7 8 9 10    (没丢)
存的游标落后超过一圈(生产者已写到 30)
  read() 的第一条返回 30,跳过 24 条(= 3 圈),随后 -> (nothing)
  (环里其实还留着 23~29;读者落在 30 之后不会回头)
```

`Reader::next_idx` 是 `public` 的、读者私有的,所以记录进程可以定期把它存到磁盘,重启时 `reader.next_idx = saved` 续读——只要落后不到一圈,消息还在环里,一条不丢;超过一圈,丢的部分就找不回来了。

还有一个和它对称的坑:**队列被重建(比如每天开盘前 `shm_unlink` 再建),老读者不重启**。新队列的序号从 0 开始,老读者的游标是几百万,`int(new_idx - next_idx) < 0` 恒成立,`read()` 一直返回 `nullptr`:读者看上去是"没有新消息",实际是**卡死**,直到新序号涨到它的游标(实测:游标 1000,新写者写 1..999 时什么都读不到,写到 1000 才恢复)。所以重建队列时读者得一起重启,或者自己检测"序号倒退了"。

### 5. 其他几处(记一下,不展开)

- 源笔记 [:169](../../trading-system-notes/chinese/01-low-latency/10-spmc共享内存无锁队列应用.md:169) 读者函数末尾 `delete q_trade_sh;`:这个指针是 `mmap` 出来的,不是 `new` 出来的,该用 `munmap`;而且它在 `while (1)` 后面,实际跑不到。
- `shmmap` 对所有人都用 `O_RDWR` + `PROT_WRITE` + 权限 `0666`。读者本来"只读不写",这样"只读"只是**约定**、不是**强制**;读者改用 `O_RDONLY` + `PROT_READ` 映射,读者里的 bug 就写不坏队列(按 API 语义推,POSIX 部分本机没跑)。
- `shmmap` 每次都 `ftruncate(fd, sizeof(Q))`:读者和写者用的结构体大小不同的话,小的那一方会把对象**截短**,大的那一方再访问被截掉的页会收到 `SIGBUS`(按 POSIX 语义推,没跑)。
- 容器里要共享,源笔记 [:217](../../trading-system-notes/chinese/01-low-latency/10-spmc共享内存无锁队列应用.md:217) 的办法是运行时加 `--ipc=host`(运维层的事)。

### 小结:三句话

1. 放进共享内存 = `shm_open` + `ftruncate` + `mmap(MAP_SHARED)`,靠"新对象全是 0"当空队列;每个进程映射的地址不同,所以元素必须自包含、不能有指针。
2. 应用层的坑都是前面讲过的东西在真实部署里的样子:第一圈缺页(第一次不要发生在热路径)、慢读者被套圈(余量 = 容量 ÷ 速率差)、重启丢消息(游标可以存)。
3. 读者不阻塞生产者,但不免费(附一):读者越多,生产者每条越贵。
