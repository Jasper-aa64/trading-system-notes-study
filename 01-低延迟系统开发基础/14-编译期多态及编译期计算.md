核心句：**这一节讲两件事，都是把运行时的工作挪到编译期。编译期多态把“调哪个实现”定在编译期，运行时没有间接跳转、还能内联；编译期计算把“这个值是多少”定在编译期，运行时直接用算好的常量或表。代价都一样：编译期必须知道答案。**

## 1. 编译期多态：五种写法，同一个思路

上一条（[#13](13-组合优先于继承.md)）和速查页第 3 条讲了静态多态和动态多态的区别：差在“调哪个函数”什么时候定。源列的五种写法都是静态多态，区别只在**编译器靠什么来选实现**：

| 写法 | 编译器靠什么选 | 讲过的地方 |
|---|---|---|
| 函数重载 | 实参的类型 | 本节 1.1 |
| 模板特化 | 模板实参（类型或常量） | 本节 1.2 |
| CRTP | 基类模板参数里写的子类 | 本笔记文末“轮 1：CRTP” |
| `if constexpr` | 编译期条件，没选中的分支不实例化 | #12 轮 3 第 4.1 节 |
| concepts / `requires` | 类型满不满足约束 | #12 轮 3 第 4.3 节 |

### 1.1 函数重载：最简单的编译期多态

同名函数，参数类型不同，编译器在调用处按实参类型选一个，选完就是一次普通的直接调用：

```cpp
const char* describe(int) { return "int"; }
const char* describe(double) { return "double"; }

describe(1);     // 调 describe(int)
describe(1.0);   // 调 describe(double)
```

运行时没有任何“选”的动作，这是它和虚函数的根本区别：虚函数按对象的**实际类型**在运行时选，重载按表达式的**静态类型**在编译时选。

### 1.2 模板特化：给某个模板实参单独写一份

**模板特化（template specialization）**：先声明一个通用模板（主模板），再为某个具体的模板实参单独给出一份实现。用到 `OrderProcessor<OrderType::BUY>` 时，编译器就用为 `BUY` 写的那份。源 :107–124（补全了 `Order`、`OrderType` 和函数体）：

```cpp
enum class OrderType { BUY, SELL };

template <OrderType Type>
struct OrderProcessor;                 // 主模板只声明、不定义

template <>
struct OrderProcessor<OrderType::BUY> {
    static void process(const Order& order) { /* 买单逻辑 */ }
};

template <>
struct OrderProcessor<OrderType::SELL> {
    static void process(const Order& order) { /* 卖单逻辑 */ }
};

template <OrderType Type>
void processOrder(const Order& order) {
    OrderProcessor<Type>::process(order);   // 编译期按 Type 选特化
}
```

几个要点：

- **主模板只声明不定义**是常见写法：哪个枚举值忘了写特化，用到时直接编译报错（不完整类型），而不是运行时走进默认分支。
- **前提是 `Type` 在编译期就知道**，写成 `processOrder<OrderType::BUY>(o)`。如果买卖方向是从行情或订单里读出来的运行时值，还是得先 `if` / `switch` 一次，再进对应的特化。这就是速查页第 3 条讲的“在外层分派一次”。
- 和 `if constexpr` 比：特化把每种情况放在不同的类里，适合每种情况代码多、或者别的模块要能自己加一种特化；`if constexpr` 把几种情况写在同一个函数里，适合每种只有几行。

### 1.3 `if constexpr` 里的 `static_assert(false)`

源 :130–135 用 `else { static_assert(false); }` 兜底：传进来的既不是 `Bear` 也不是 `Duck` 就编译报错。这种写法在 GCC 13、Clang 18 上能过（实测，`-std=c++20` 也能过）：C++ 标准后来把“没走到的分支里的 `static_assert(false)` 不报错”当成缺陷修正，追溯到了旧标准。更早的编译器会不管有没有走到都直接报错。要兼容旧编译器，写成依赖模板参数的条件：

```cpp
template <typename> inline constexpr bool always_false = false;

template <typename Animal>
const char* speak(const Animal& a) {
    if constexpr (std::is_same_v<Animal, Bear>) return a.roar();
    else if constexpr (std::is_same_v<Animal, Duck>) return a.quack();
    else static_assert(always_false<Animal>, "unsupported animal");
}
```

`always_false<Animal>` 的值要等 `Animal` 确定了才知道，所以只有真的实例化到这个分支时才会触发。

### 1.4 concepts 在这里的角色

源 :59–101 的 `GraphBuilder` 例子里，真正“多态”的是 `process_graph` 这个函数模板：传 `BuilderA` 和 `BuilderB` 各实例化一份。concept 本身不负责选实现，它负责**把“这个类型能不能用”写成一个有名字的条件**：不满足的类型在调用处就报错，报错信息是“约束不满足”，而不是模板里面几十行的展开错误。（源这段代码不完整，`HasBuildGraph`、`Graph` 都没定义，`(...)` 也不是合法代码，只能当示意读。）

## 2. 编译期计算：`const` / `constexpr` / `consteval` / `constinit`

四个关键字长得像，回答的是不同的问题。先给一张对比表，再逐个讲：

| 关键字 | 修饰什么 | 保证在编译期算出来吗 | 之后能改吗 |
|---|---|---|---|
| `const` | 变量、参数、成员函数 | **不保证** | 不能 |
| `constexpr` | 变量 | 保证 | 不能 |
| `constexpr` | 函数 | 不保证：用在要求常量的地方才在编译期算 | — |
| `consteval` | 函数 | 保证：每次调用都在编译期算 | — |
| `constinit` | 静态生命周期的变量 | 保证初始化在编译期完成 | **能**（不带 `const`） |

### 2.1 `const`：只读，不是“编译期常量”

`const` 只说一件事：**初始化之后不能再改**。初始值可以是运行时才知道的，比如 `const int scale = get_config("scale");`。

对性能要分清两种情况：

- **`const` 对象本身**：比如 `const int max_len = 100;`。改它是未定义行为，编译器可以认定它不变，直接把 100 当立即数用。整型的 `const` 变量用常量初始化时，还能当编译期常量用（下面 2.5 的 `Vector<vec_dim>`）。
- **`const T*` / `const T&`**：只是说**你**不能通过这个指针改它，不代表别人不会改。编译器照样要防着别的指针写过它。实测：

```cpp
int f(const int* p, int* q) {
    int a = *p;
    *q = 1;          // q 可能和 p 指向同一个 int
    return a + *p;   // 所以这里要重新读 *p
}
```

GCC `-O2` 编出来是 `movl (%rdi), %eax` → `movl $1, (%rsi)` → `addl (%rdi), %eax`，`*p` 读了两次。所以“参数加 `const` 能让编译器优化”基本不成立，`const &` 参数的好处是不拷贝、防误改。想让编译器认定两个指针不重叠，靠的是 `__restrict`（#16 指针访存优化会讲）。

源里 `const` 和 `#define` 的对比表（:164–169）是对的：`const` 有类型、守作用域，宏只是文本替换。

### 2.2 `constexpr`：变量一定编译期算，函数“能”编译期算

源 :224 说 `constexpr` 是“优化提示”、“若可编译期计算则必须在编译期完成”，这不对，已改正。`constexpr` 修饰变量和修饰函数，意思不一样：

- **`constexpr` 变量**：初始值**必须**在编译期算出来，算不出来就编译报错。`constexpr int scale = get_config("scale");` 报错，因为 `get_config` 要运行时才能调。
- **`constexpr` 函数**：意思是“**允许**在编译期算”。用在要求常量的地方（`constexpr` 变量的初始值、模板实参、数组大小、`static_assert`），编译器必须在编译期算；用在普通表达式里、参数是运行时的值，就是一次普通的运行时调用。

```cpp
constexpr int twice(int x) { return x + x; }
constexpr int four = twice(2);          // 编译期算出 4
int twice_rt(int n) { return twice(n); } // n 运行时才知道：运行时算
```

`twice_rt` 编出来就是一条 `leal (%rdi,%rdi), %eax`，和普通函数一样。参数是常量但不在要求常量的地方（比如 `int x = twice(2);`），标准不要求编译期算，只是优化器一般会顺手算掉。

源 :235–238 列的限制（不能有 `static` 局部变量、不能调非 `constexpr` 函数）是旧标准的说法。C++23 起这些可以**写**在 `constexpr` 函数里，只是编译期求值时不能**走到**它们。源自己在 :395 也是这么说的。

### 2.3 `consteval`：每次调用都必须在编译期

`consteval` 函数叫**立即函数（immediate function）**：每次调用都必须在编译期算完，参数不是常量就编译报错。用在“这个值必须编译期就有，运行时算就是 bug”的地方，比如编译期校验一个配置、生成一个哈希值。

```cpp
consteval int get_dim() { return 4; }
Vector<get_dim()> v;     // 可以当模板实参
```

源 :421 的陷阱说得对：`consteval` 函数的**形参在函数体里不是常量表达式**。虽然每次调用都在编译期，但函数体是按“一个普通参数”来写的，不能 `static_assert(i == 1)`，也不能拿 `i` 当模板实参。要用就得让它变成模板参数（`template <int I>`）。

### 2.4 `constinit`：静态变量在编译期初始化，但可以改

源 :244–251 有两处不对，已改正：`constinit` **不**隐含 `const`，初始化之后可以改；它和 `consteval` 也没有关系。`constinit` 只管一件事：**静态生命周期的变量（全局变量、`static` 变量）的初始化必须在编译期完成**。

```cpp
constexpr int somefunc() { return 27; }    // 必须是 constexpr
constinit int g_counter = somefunc();      // 编译期初始化成 27
// ...
++g_counter;                               // 可以改，变成 28
```

GCC 把 `g_counter` 放在 `.data` 段，初值 27 直接写在可执行文件里，程序一启动就是 27，没有运行时初始化的代码。

它解决的问题：全局变量如果是运行时初始化的（初始值来自普通函数调用），由启动代码在 `main` 之前去算。不同源文件里的全局变量谁先初始化，标准不规定，一个全局变量的初始化读了另一个还没初始化的，就是 bug（static initialization order fiasco，静态初始化顺序问题）。`constinit` 让这件事在编译期就有保证，做不到就编译报错。

源 :258–269 的例子里 `somefunc()` 是普通函数，`constinit` 那行会编译失败；`#ifdef` 是预处理阶段选的分支，和 `constinit` 无关。正确写法是把 `somefunc` 写成 `constexpr`，如上。

### 2.5 非类型模板参数：把一个常量变成类型的一部分

**非类型模板参数（NTTP，non-type template parameter）**：模板参数不是类型，而是一个值。源 :281–299（去掉了 `template <const int Dim>` 里多余的 `const`，模板参数本来就是常量）：

```cpp
template <int Dim>
struct Vector {
    float data[Dim];
    float dot(const Vector& other) const {
        float sum = 0.0f;
        for (int i = 0; i < Dim; i++) sum += data[i] * other.data[i];
        return sum;
    }
};

const int vec_dim = 4;
Vector<vec_dim> v1, v2;     // Vector<4>：循环次数是编译期常量
```

`Dim` 是类型的一部分：`Vector<4>` 和 `Vector<8>` 是两个不同的类型，各编一份代码，循环次数是常量，编译器可以整个展开或向量化，不用在运行时判断维度。代价就是速查页第 3 条讲的代码膨胀：每个维度一份。

能当模板实参的必须是编译期常量。`const int vec_dim = 4;` 可以（整型 `const`、用常量初始化），`int n = 4; const int runtime_dim = n;` 不行，因为 `n` 不是常量（源 :376–378 说得对）。

### 2.6 `if consteval`（C++23）：同一个函数，编译期和运行时走两套实现

```cpp
constexpr std::size_t my_strlen(const char* s) {
    if consteval {
        std::size_t n = 0;          // 编译期：一个字节一个字节数
        while (s[n]) ++n;
        return n;
    } else {
        return std::strlen(s);      // 运行时：用库里优化过的版本（std::strlen 不是 constexpr）
    }
}
static_assert(my_strlen("hello") == 5);
```

用途是：编译期只能用 `constexpr` 能跑的写法，运行时想用更快的实现（库函数、SIMD、内联汇编），两边共用一个函数名。

### 2.7 怎么选

- 值必须编译期就有，算不出来应该报错 → `constexpr` 变量，或者 `consteval` 函数。
- 一份实现编译期、运行时都要用 → `constexpr` 函数，需要的话加 `if consteval`。
- 全局 / `static` 变量，要可改，但不想要运行时初始化 → `constinit`。
- 只是不想被改 → `const`。

## 3. 查找表（LUT）与预计算：用空间换时间

**查找表（LUT，lookup table）**：提前把结果算好放进数组，运行时按下标取。#12 轮 2 的 `fee_lookup`、编译器把 `switch` 换成的 `CSWTCH` 值表都是这个。

源 :438–445 把“什么时候算”分成四个时机：

| 时机 | 怎么做 | 适合 |
|---|---|---|
| 编译前（离线） | 另写程序生成数据文件或 C++ 源码 | 很大、很少变的表 |
| 编译时 | `constexpr` 函数填数组 | 能用常量算出来的小表 |
| 程序启动时 | 初始化函数填表 | 依赖配置的表 |
| 第一次用到时 | 延迟计算 | 很少用到的表（要注意线程安全，第一次调用慢） |

编译时生成的例子：

```cpp
constexpr std::array<uint64_t, 20> make_pow10() {
    std::array<uint64_t, 20> t{};
    uint64_t v = 1;
    for (auto& x : t) { x = v; v *= 10; }
    return t;
}
constexpr auto kPow10 = make_pow10();     // 编译期填好，放进 .rodata
uint64_t pow10(unsigned e) { return kPow10[e]; }
```

`kPow10` 在 `.rodata`（只读数据段），20 个值直接写在可执行文件里；`pow10` 编出来是 `leaq kPow10(%rip), %rax` + `movq (%rax,%rdi,8), %rax`，一次读内存。

要记的代价：**查表是一次读内存，表大了会缓存未命中**。表在 L1D 里，一次读约 1 ns；表大到几十 KiB 以上、访问又随机，就会落到 L2、L3 甚至内存（[11补](11-补-内存层级-延迟与带宽.md)），这时候直接算可能比查表快。几次乘法加法能算出来的东西，不一定值得做成表。

## 4. 还没法验证的两个 C++26 特性

- **`std::nontype_t`**（源 :305–355）：把一个常量通过参数类型带进普通函数，让它在函数体里当模板参数用，主要给 `std::function_ref` 用。GCC 13 没有实现，这里不展开。（我印象里后来的 C++26 草案把它换成了更通用的 `std::constant_wrapper`，没有核实。）
- **`template for`**（源 :448–462）：编译期循环，编译器把循环体按次数复制展开，每次的循环变量是常量。源写的 `0..4` 不是 C++ 语法，实际要写成遍历一个编译期的序列（比如 `std::array` 或参数包）。GCC 13 不支持，没有验证。

## 轮 1：CRTP（奇异递归模板）：让基类在编译期知道子类是谁

核心句：**CRTP 是子类把自己当模板参数传给基类，基类于是在编译期就知道“我是谁的基类”，可以直接 `static_cast` 成子类去调它的函数。效果和虚函数一样是“基类写流程、子类填细节”，但选哪个函数在编译期定，调用能内联，对象里没有 vptr；代价是不同子类没有共同的基类，放不进同一个容器。**

本轮按这个顺序讲：1 是什么、为什么合法 → 2 编译出来和虚函数差在哪 → 3 三种用途 → 4 四个坑 → 5 和虚函数对比 → 6 C++23 的替代写法 → 7 面试常怎么问。

### 1. 是什么：子类把自己传给基类

**场景**：行情网关接好几个交易所的行情。每个交易所的处理流程大体一样（收包、校验序号、更新订单簿），只有“解析一条消息”这一步各不相同。很自然的写法是基类写流程，子类填“解析”这一步。用虚函数写，基类调 `virtual on_tick()`，运行时按对象的类型选。这一步每秒要调几百万次，每次都多两笔开销：一是**间接跳转**，编译器不知道是哪个子类，只能生成“读 vtable、取出函数地址、再跳过去”的代码，CPU 要先猜跳到哪，猜错一次约 15–20 个周期；二是**没法内联**，内联是编译器把被调函数的函数体直接抄进调用处，不知道调到哪个子类就不知道抄哪一份，只能保留一次真正的函数调用。

CRTP 的做法是让基类在编译期就知道子类是谁。源 :10–51（逐字，省掉了 `main`）：

```cpp
// 基类模板
template <typename Derived>
class Base {
public:
    // 调用派生类的具体实现
    void doSomething() {
        static_cast<Derived*>(this)->doSomethingImpl();
    }
};

// 派生类
class Derived1 : public Base<Derived1> {
public:
    // 派生类的具体实现
    void doSomethingImpl() {
        std::cout << "Derived1 is doing something." << std::endl;
    }
};

// 辅助函数，接受基类引用并调用其doSomething方法
template <typename T>
void performAction(Base<T>& obj) {
    obj.doSomething();
}
```

**名字的由来**：`class Derived1 : public Base<Derived1>`，一个类在自己的定义里，把自己当成基类的模板实参，看起来像是“递归”了，所以叫 curiously recurring template pattern（奇异递归模板模式）。

**为什么合法**：写到 `Base<Derived1>` 那一刻，`Derived1` 还没定义完，是个**不完整类型**（incomplete type）：编译器只知道有这么个类，不知道它有哪些成员、多大。`Base<Derived1>` 能实例化，是因为 `Base` 的类定义里没用到 `Derived` 的任何成员，只在 `doSomething()` 的**函数体**里用了。类模板的成员函数体要等真被调用时才实例化，那时 `Derived1` 早已定义完。这一点决定了第 4.3 节的坑。

**为什么 `static_cast` 是安全的**：从基类指针转成子类指针（向下转型），只要这个对象**真的是**那个子类，`static_cast` 就是正确的，而且不需要运行时检查，编译出来通常什么指令都没有（单继承时基类子对象和子类对象地址相同）。CRTP 靠约定保证这一点：只有 `Derived1` 会继承 `Base<Derived1>`。约定被打破时会出什么事，见第 4.1 节。

### 2. 编译出来：和虚函数差在哪

同一个 `on_tick`，一个用 CRTP，一个用虚函数（[14-crtp-check.cpp](14-crtp-check.cpp)）：

```cpp
template <typename Derived>
struct FeedBase {
    int on_tick(int px) { return static_cast<Derived*>(this)->on_tick_impl(px); }
};
struct BinanceFeed : FeedBase<BinanceFeed> {
    int mult = 2;
    int on_tick_impl(int px) { return px * mult; }
};
template <typename T>
int run_crtp(FeedBase<T>& f, int px) { return f.on_tick(px); }

struct IFeed {
    virtual ~IFeed() = default;
    virtual int on_tick(int px) = 0;
};
struct OkxFeed : IFeed {
    int mult = 3;
    int on_tick(int px) override { return px * mult; }
};
int run_virtual(IFeed& f, int px) { return f.on_tick(px); }
```

GCC 13 `-O2` 编出来：

```text
run_crtp<BinanceFeed>:           run_virtual（程序里只有 OkxFeed 一个实现）：
    movl  (%rdi), %eax               movq  (%rdi), %rax           # 读 vptr
    imull %esi, %eax                 leaq  OkxFeed::on_tick, %rdx
    ret                              movq  16(%rax), %rax         # 读 vtable 那一格
                                     cmpq  %rdx, %rax             # 是不是 OkxFeed::on_tick？
                                     jne   .L18                   # 不是：去做间接调用
                                     movl  8(%rdi), %eax          # 是：走内联好的版本
                                     imull %esi, %eax
                                     ret
```

- **CRTP**：`on_tick` → `on_tick_impl` 全部内联，只剩“读 `mult`、乘”两条指令。`mult` 在偏移 0，因为对象里没有 vptr。
- **虚函数**：GCC 在这里做了**推测性去虚化**（speculative devirtualization）：它看到整个程序只有 `OkxFeed` 一个实现，就先比较 vtable 那一格是不是 `OkxFeed::on_tick`，是的话走内联好的版本。即便如此，也还要多读 vptr、读 vtable、比较一次。程序里再加一个 `BybitFeed : IFeed`，实测 `run_virtual` 就变回了 `movq (%rdi), %rax` + `jmp *16(%rax)`：一次纯粹的间接跳转，`on_tick` 的函数体没法内联进来。
- **对象大小**：`sizeof(BinanceFeed)` 是 4（只有一个 `int`，空基类不占空间），`sizeof(OkxFeed)` 是 16（vptr 8 字节 + `int` 4 字节 + 补齐 4 字节）。

省下来的东西，就是[速查页 1.3](https://jasper-aa64.github.io/zh/ref/cpp-syntax/#virtual-cost) 列的那几条：要猜的间接跳转、两次读内存、vptr 的 8 字节，以及最值钱的内联。

〔补〕**为什么说内联最值钱**（用户问：是因为一次间接跳转 3–5 ns 不算多吗）：一次间接跳转猜对时只多几个周期，不到 1–2 ns；4–5 ns 是**猜错一次**的代价。同一处调用目标固定（一个 feed 收一串行情）时几乎总猜对，所以单看一次调用，虚函数没慢多少。差距在循环里：对 n 个价格求和（`sum_crtp` / `sum_virtual`，见验证程序），GCC 13 `-O2` 下 CRTP 版把“读 `mult`”提到循环外只做一次，每个价格只剩读、乘、加，`-O3` 还向量化成 `pmuludq` 一次 4 个；虚函数版每轮读 vptr、`call *16(%rax)`，被调函数里再读一次 `mult`（看不见函数体，不敢假设它没变），进函数先存 4 个寄存器，向量化不可能。内联省的不是跳转那几个周期，是让编译器能把调用和前后代码一起优化（外提、合并、向量化）。

### 3. 三种用途

#### 3.1 静态接口：替代热路径上的虚函数

就是第 1、2 节的例子：基类写流程（收包、校验序号），在某一步调子类的钩子；子类只实现钩子。行情处理、策略回调这种每秒几百万次、而且部署时就知道是哪个交易所的地方最常用。源 :53 说的“处理外部数据源的接口”就是这个。

#### 3.2 往子类里注入功能：子类写一点，基类补全其余

基类知道子类类型，就能写出“基于子类已有的函数”的通用代码。例如子类只写 `==`，基类给出 `!=`：

```cpp
template <typename Derived>
struct EqualityOps {
    friend bool operator!=(const Derived& a, const Derived& b) { return !(a == b); }
};
struct Price : EqualityOps<Price> {
    long ticks;
    friend bool operator==(const Price& a, const Price& b) { return a.ticks == b.ticks; }
};
```

`!=` 这个例子在 C++20 里已经不需要了：写了 `==`，编译器自动支持 `!=`。标准库里至今常用的 CRTP 是 `std::enable_shared_from_this<T>`。

〔补〕**`std::enable_shared_from_this`：在成员函数里拿到自己的 `shared_ptr`**（用户问：之前见过，不知道是什么）。

- **场景。** 一个 `Session` 代表一条 TCP 连接，由 `std::shared_ptr` 管理。`shared_ptr` 是带引用计数的智能指针：计数存在一块单独的**控制块**里，第一次把对象交给 `shared_ptr`（如 `std::make_shared`）时分配；之后每复制一个 `shared_ptr` 计数 +1，销毁一个 -1，减到 0 才析构对象。`Session::start()` 发起一次异步读，把回调交给事件循环，回调以后才跑。到那时外面的 `shared_ptr` 可能已经没了，所以回调自己得持有一个 `shared_ptr<Session>`，保证对象还活着。可是在成员函数里，手上只有 `this`，一个裸指针。
- **错误写法：`std::shared_ptr<Session>(this)`。** 这会再分配一个新的控制块。两个计数各数各的：外面那份数到 0 就把对象析构了，回调里那份还指着它（悬空）；等它也数到 0，再 delete 一次。GCC 13 实测程序直接 abort（`munmap_chunk(): invalid pointer`），ASan 报 bad-free。
- **正确写法：公有继承它，调 `shared_from_this()`。**

  ```cpp
  std::vector<std::function<void()>> g_loop;     // 假装是事件循环：回调先存起来，以后再跑
  struct Session : std::enable_shared_from_this<Session> {
      int id = 7;
      void start() {
          auto self = shared_from_this();        // 计数 +1，和外面那个 shared_ptr 共用控制块
          g_loop.push_back([self] { std::printf("cb %d\n", self->id); });
      }
  };
  // { auto s = std::make_shared<Session>(); s->start(); }   // s 没了，Session 还活着
  // for (auto& cb : g_loop) cb();                           // 打印 cb 7
  // g_loop.clear();                                         // 最后一个 shared_ptr 没了，这时才析构
  ```

- **它怎么做到的。** `enable_shared_from_this<Session>` 里藏了一个 `std::weak_ptr<Session>` 成员。`weak_ptr` 指向控制块，但不让计数 +1，也就不让对象活着。`make_shared` 建对象时发现它继承了 `enable_shared_from_this`，就把这个 `weak_ptr` 指向刚建好的控制块。`shared_from_this()` 就是把它升级成 `shared_ptr`：同一个控制块，计数 +1。
- **为什么必须是 CRTP。** 这个 `weak_ptr` 成员的类型和 `shared_from_this()` 的返回类型都得写成 `Session`，基类只有拿到 `T` 才写得出来。基类如果不是模板，就只能存、只能返回 `shared_ptr<基类>`，回调里每次用都要先 `static_pointer_cast` 转回 `shared_ptr<Session>`，转错了就是未定义行为。
- **三个坑**（GCC 13 实测，见验证程序）：
  - 对象必须已经归 `shared_ptr` 管。栈上的对象，或者在构造函数里调（这时 `make_shared` 还没填 `weak_ptr`），C++17 起抛 `std::bad_weak_ptr`，更早的标准是未定义行为。
  - 必须 `public` 继承。私有继承时 `shared_ptr` 看不见这个基类，`weak_ptr` 没人填，同样抛 `bad_weak_ptr`。
  - 有代价：对象多一个 `weak_ptr`（两个指针，16 B；实测 `sizeof(Session)` 是 24，含对齐填充）；每次 `shared_from_this()`、每次复制 `shared_ptr` 都是一次原子加，计数所在的缓存行还可能在多个核之间来回抢（缓存行乒乓）。所以它用在连接管理这种冷路径上（Asio 风格的异步服务器里回调常写成 `[self = shared_from_this()]`），热路径上不来回复制 `shared_ptr`。

#### 3.3 每个子类一份独立的静态成员

`Base<A>` 和 `Base<B>` 是两个不同的类型，所以基类里的 `static` 成员也是各一份。用来给每种对象单独计数：

```cpp
template <typename Derived>
struct InstanceCounter {
    static inline int alive = 0;
    InstanceCounter() { ++alive; }
    InstanceCounter(const InstanceCounter&) { ++alive; }
    ~InstanceCounter() { --alive; }
};
struct OrderA : InstanceCounter<OrderA> {};
struct OrderB : InstanceCounter<OrderB> {};
```

实测建了 3 个 `OrderA`、2 个 `OrderB`，各析构一个以后，`InstanceCounter<OrderA>::alive` 是 2，`InstanceCounter<OrderB>::alive` 是 1，互不干扰。如果用一个普通基类，`static` 成员只有一份，就分不开了。

### 4. 四个坑

#### 4.1 基类的模板实参抄错：静默算错

```cpp
template <typename D> struct Base { int run() { return static_cast<D*>(this)->impl(); } };
struct A : Base<A> { int x = 1; int impl() { return x; } };
struct B : Base<A> { long y = 2; int impl() { return 99; } };   // 复制 A 的代码，基类忘了改
```

`B b; b.run();` 编译不报错，实测输出 2：`run()` 把一个 `B` 对象当成 `A` 转过去，调的是 `A::impl()`，读的是“`A` 的 `x` 所在的位置”，那里其实是 `B` 的 `y`。这是未定义行为，编译器不检查，因为向下转型的 `static_cast` 本来就信任程序员。

**防法**：基类构造函数设成私有，只让模板实参那个类当友元：

```cpp
template <typename Derived>
class SafeBase {
public:
    void run() { static_cast<Derived*>(this)->run_impl(); }
private:
    SafeBase() = default;
    friend Derived;                    // 只有 Derived 能构造 SafeBase<Derived>
};
struct GoodA : SafeBase<GoodA> { void run_impl() {} };
struct BadB : SafeBase<GoodA> { void run_impl() {} };   // 抄错了基类
BadB b;                                                  // 编译报错：构造不了
```

`BadB` 的定义本身能过，一构造对象就要调 `SafeBase<GoodA>` 的构造函数，可它只对 `GoodA` 开放，GCC 报 `SafeBase() ... is private within this context`。抄错的子类一旦被用到就编译失败。

#### 4.2 子类忘了写实现、名字又和基类一样：无限递归

```cpp
template <typename D> struct Base { int area() { return static_cast<D*>(this)->area(); } };
struct Sq : Base<Sq> { };   // 忘了写 area()
```

`Sq` 里没有 `area()`，`static_cast<Sq*>(this)->area()` 找到的就是继承来的 `Base<Sq>::area()` 自己，调用自己，直到栈溢出。GCC `-Wall` 会警告 `infinite recursion detected`，但只是警告。所以源的写法把子类的函数叫 `doSomethingImpl`，和基类的 `doSomething` 不同名：忘了写，就是“没有这个成员”的编译错误。

#### 4.3 基类的类定义里用不了子类的类型成员

```cpp
template <typename D> struct Base { using value_type = typename D::value_type; };
struct C : Base<C> { using value_type = int; };   // 编译错误
```

GCC 报 `invalid use of incomplete type 'struct C'`。原因就是第 1 节说的：实例化 `Base<C>` 时 `C` 还没定义完。函数体里可以用（那时 `C` 已经完整），类定义里（成员类型、成员变量的类型、函数签名）不行。要用就多传一个模板参数，或者另写一个 traits 模板放子类的类型信息。

#### 4.4 没有共同的基类：放不进同一个容器

`Base<Derived1>` 和 `Base<Derived2>` 是两个毫无关系的类型，没有 `std::vector<Base*>` 这种东西。所有接受它的函数也得是模板（源的 `performAction` 就是 `template <typename T> void performAction(Base<T>&)`）。要把不同子类放在一起，见速查页第 3.3 节的几种办法：`std::variant` + `std::visit`（类型集合固定）、按类型分批各跑一个循环、或者外层用一次虚函数选中、里面全是 CRTP。

### 5. CRTP 和虚函数对比

| | 虚函数 | CRTP |
|---|---|---|
| 调哪个函数什么时候定 | 运行时，按对象的实际类型 | 编译时，按基类的模板实参 |
| 一次调用 | 读 vptr、读 vtable、间接跳转 | 直接调用，通常内联掉 |
| 对象大小 | 多一个 vptr（8 字节） | 不变 |
| 放进同一个容器 | 可以（`vector<unique_ptr<Base>>`） | 不行，`Base<A>` 和 `Base<B>` 无关 |
| 加新的子类 | 不用重编调用方，插件也行 | 用到它的模板都要重新实例化 |
| 写错的后果 | 漏写 `override` 的函数可能没覆盖上 | 基类抄错静默 UB；同名会无限递归 |

选的规则和[速查页第 3.4 节](https://jasper-aa64.github.io/zh/ref/cpp-syntax/#poly-choose)一样：类型在编译期能定、在热路径上，用 CRTP；要放进一个容器、要运行时加类型，用虚函数。

### 6. C++23 的替代写法：deducing this

C++23 允许把 `this` 写成成员函数的第一个显式参数（explicit object parameter，常叫 deducing this），类型由编译器按调用的对象推导。基类于是不用模板参数也能拿到子类类型：

```cpp
struct FeedBase23 {
    template <typename Self>
    int on_tick(this Self&& self, int px) { return self.on_tick_impl(px); }
};
struct BybitFeed : FeedBase23 {
    int on_tick_impl(int px) { return px * 4; }
};
```

`bybit.on_tick(3)` 时 `Self` 推导成 `BybitFeed&`，`self.on_tick_impl` 直接调到子类，效果和 CRTP 一样，但第 4.1 节的“基类抄错”不存在了（没有模板实参可抄），`FeedBase23` 也成了一个普通类。Clang 18 `-std=c++23` 实测结果正确；GCC 14 起支持，GCC 13 不支持。现有代码和面试里还是 CRTP 为主。

### 7. 面试常怎么问

- **“CRTP 是什么，解决什么问题？”** 讲第 1 节的场景和代码，一句话落在“编译期多态：基类在编译期知道子类，调用能内联，没有 vptr”。
- **“和虚函数比，快在哪？”** 用第 2 节：不是“省一次跳转”那么简单，最值钱的是内联；顺带说一句编译器在只有一个实现时也能推测性去虚化。
- **“有什么缺点？”** 第 4.4 节的“没有共同基类”最重要，再加代码膨胀（每个子类实例化一份）。
- **“`static_cast` 安全吗？”** 第 1 节和第 4.1 节：约定成立时安全，抄错基类是静默 UB，用私有构造 + `friend Derived` 防。
- **“标准库里哪里用了？”** `std::enable_shared_from_this`。
