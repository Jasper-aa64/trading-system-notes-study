核心句：**这一节讲三件事。一是告诉编译器两个指针不重叠，它才敢少读几次内存、敢向量化（`__restrict`）；二是数据怎么存得更省：链式结构里“下一个在哪”用多少字节存，它决定每走一步要几条指令、整条链能装进哪一层缓存，指针和几个 ID 又怎么压进一个整数；三是大块写和写设备时，用什么指令写**。

## 1. `__restrict`：向编译器保证两个指针不重叠

### 1.1 别名（aliasing）：两个指针可能指向同一块内存

两个指针指向同一块内存，叫它们互为**别名**。编译器看到通过一个指针写，就得假设另一个指针读到的值可能变了。源 :10：

```cpp
void func(int *a, int *b, int n) {
    for (int i = 0; i < n; ++i) {
        a[i] = *b;
    }
}
```

`b` 可能就指向 `a` 里的某一格，写 `a[i]` 可能改掉 `*b`。所以 GCC `-O2` 每轮都重读 `*b`：

```text
.L3:
    movl  (%rsi), %eax      # 每轮读一次 *b
    addq  $4, %rdi
    movl  %eax, -4(%rdi)    # 写 a[i]
    cmpq  %rdx, %rdi
    jne   .L3
```

加上 `__restrict`（源 :19 的 `func_restrict`），意思是“在这个函数里，通过这个指针访问的内存，不会通过别的指针访问”。编译器就把 `movl (%rsi), %eax` 提到循环外，只读一次，循环里只剩写（还顺手展开成每轮写 2 个）。

### 1.2 `-O3`：编译器自己在运行时检查一遍

`-O3` 下，不带 `__restrict` 的 `func` 也向量化了。编译器生成了两个版本的循环，开头先比地址：`b` 不落在 `a[0..n)` 里，就走一次写 16 B 的向量版；落在里面，就走每轮重读 `*b` 的逐个版。这叫**循环多版本**（loop versioning）。所以 `-O3` 下 `__restrict` 省的是开头这几条比较和那份备用代码；`-O2` 下，或者别名关系复杂到编译器不愿生成检查时，差别才大。

### 1.3 代价：这是你的承诺，编译器不检查

- **违反了就是未定义行为。** 你写了 `__restrict`，调用时又传了重叠的指针，编译器照样按“不重叠”优化，结果静默算错，没有任何报错。
- **它只影响编译器，CPU 看不见。** 机器码里没有“restrict”这回事，它的效果全在“编译器生成了哪些指令”。源 :18 的注释说它帮 CPU“简化存储转发、减少依赖检查”，不对：CPU 照样检查每个读和前面的写是否同址。
- **不是标准 C++。** C99 有 `restrict`，C++ 没有；GCC、Clang、MSVC 都支持 `__restrict` 扩展。
- **类型不同时本来就不用写。** `int*` 和 `float*` 按严格别名规则（strict aliasing）默认不重叠；`__restrict` 管的是同一种类型的两个指针。[#14 §2.1](14-编译期多态及编译期计算.md) 讲过，`const T*` 不能代替它。

## 2. 链式结构里“下一个”存多宽

### 2.1 前提：pointer chasing 每一步都要等上一步

链表、订单簿的价位链、对象池的空闲链，都是“读出下一个在哪，再去读它”。下一次读的地址，要等这一次读完才知道，所以这种 **pointer chasing** 没法提前发读（[11补 轮 1](11-补-内存层级-延迟与带宽.md)），每一步都付满一次访存延迟：L1 约 1 ns（4–5 个周期），L2 约 3–5 ns，L3 约 10–30 ns，内存约 70–120 ns。链全在 L1 里时，一步只要几个周期，多一条指令就看得出来；链落到内存，每一步都是一次完整的内存延迟，多几条指令无关紧要，要紧的是链能不能小到落进更近的一层。所以链快不快只看两件事：**每一步的指令要多久**，**整条链有多大**。“下一个”存多宽，同时影响这两件事。

### 2.2 下标还是指针：寻址方式差 1 个周期，大小差 1 倍

源 :41 用 4 字节下标存“下一个是第几个”，源 :68 用 8 字节指针。编出来每步各是一条指令：

```text
chase_int:   movslq (%rcx,%rax,4), %rax     # 基址 + 下标 × 4，读 4 字节并扩成 64 位
chase_ptr:   movq   (%rax), %rax            # 直接按指针读 8 字节
```

源 :64 说下标版“地址计算需乘法（k*4）”，不对：`× 4` 是 x86 寻址方式的一部分（scale），不是一条乘法指令。两者真正的差别在寻址方式：很多 x86 核上，只有“一个寄存器（加一个小偏移）”的简单寻址，L1 命中时约 4 个周期出结果；带下标的寻址约 5 个周期。所以全在 L1 时，指针链每步快约 1 个周期。源 :90 用“存储转发 / 绿色通道”解释这一点，说法不对，原因就是这里的寻址方式。

反过来，指针是 8 字节，下标是 4 字节，同样多的节点，指针链大一倍。1024 个节点是 8 KiB 对 4 KiB，都在 L1 里，指针快；100 万个节点是 8 MiB 对 4 MiB，下标版可能还在 L3、指针版已经要读内存，那一步差的就是 10–30 ns 对 70–120 ns，1 个周期的寻址优势完全不算数。**链小时看指令，链大时看字节数。**

### 2.3 “32 位指针”：64 位程序里通常就是下标

指针快在寻址，下标赢在大小，自然会想两头都要：让指针本身只占 4 字节，拿来就能直接读。这就是源 :101 的“32 位指针”，写法是把地址强转成 `uint32_t` 存，用的时候再转回指针。

64 位程序里一般做不到，因为 4 字节装不下地址。4 字节最多表示到 4 GiB（`0xffffffff`），而 64 位程序的地址一般远在这之上，Linux 上常见 `0x7ffd5a3c1e80` 这样的。把地址直接转成 `uint32_t`，g++ 会报错（`cast ... loses precision`，意思是转了会丢信息）；硬转（先转成 `uintptr_t` 再截成 `uint32_t`）能编过，但高位被扔掉，转回指针就指到别处了。

4 字节能存下的，只有“下一个在数组里排第几”（或者离数组开头多少字节）。要跳过去，得先算“数组起点 + 第几个 × 节点大小”，这就是上面的下标版，那 1 个周期照样要付。**所以“32 位指针”多数时候只是下标换了个叫法**，指针和下标之间的取舍还是绕不开。

例外有两种：节点本来就放在 4 GiB 以下（比如 Linux 上用 `mmap` 加 `MAP_32BIT` 申请的内存，落在最低的 2 GiB 里），这时 4 字节存的就是完整地址，可以直接读；或者整个程序换成 4 字节指针的编法（编成 32 位程序 `-m32`，或者很少有人用的 x32 `-mx32`）。

另外源 :48 的 `std::random_shuffle` 在 C++17 已删除，验证程序换成了 `std::shuffle`。

### 2.4 24 位紧凑下标：省 25% 空间，每步多几条指令

下标版的链如果只比某一层缓存大一点，还可以再压一压：源 :116 每个元素只占 3 字节，比 4 字节下标省 25%。代价是每走一步要读 3 个字节再拼起来：

```cpp
int next_val = q[k] | (q[k+1] << 8) | (q[k+2] << 16);
k = next_val & MASK_24;
```

编出来每步是 3 次读、2 次移位、2 次或，还有几条算地址、扩展符号的指令，而它们都在依赖链上。全在 L1 时它比 4 字节下标慢；只有省下的 25% 正好让整条链从下一层缓存“掉回”上一层，才划算。

容量也要算对：这段代码存的是**字节偏移**（下标 × 3），24 位最大 $2^{24} - 1$，所以最多约 $2^{24} / 3 \approx 559$ 万个元素，不是源 :144 说的约 1600 万。想要 1600 万个，就存下标本身，每步再乘 3（一条 `lea`）。

## 3. 指针压缩：存偏移，不存地址

下标能用，前提是池子里每个元素一样大：第 k 个就在“起点 + k × 元素大小”。对象大小不一，或者几种类型混放在同一块内存里（订单和价位节点挤在一块 arena 里，长短不一的消息排在一块缓冲区里），就没有“第几个”可言，只能记字节位置：离池子开头多远。

直接存字节偏移，4 字节只能管 4 GiB。可对象一般按 $2^s$ 字节对齐，每个对象的起点都是 $2^s$ 的倍数，偏移的低 $s$ 位永远是 0，存它们纯属浪费。把偏移右移 $s$ 位再存，用的时候左移回来：

$$
\text{编码} = \frac{\text{地址} - \text{基址}}{2^{s}}, \qquad \text{地址} = \text{基址} + \text{编码} \times 2^{s}
$$

比如按 16 字节对齐（$s = 4$），对象在离池子开头 `0x1230` 字节处，低 4 位是 0，只存 `0x123`；用的时候左移 4 位变回 `0x1230`，再加上池子的起点。同样 4 字节，能管的范围从 4 GiB 变成 $2^{32} \times 16$ B = 64 GiB。

这样看，下标其实是它的特例：对象一样大、大小正好是 $2^s$ 时，右移 $s$ 位的偏移就是下标。两者只是单位不同：下标以“一个元素”为单位，压缩指针以“对齐粒度 $2^s$”为单位。正因为单位是对齐粒度，它能指向池子里任何一个对齐的对象，不管什么类型、多大。容量上它并不比下标强：同样 4 字节，下标能管 $2^{32}$ 个元素，元素越大，管的字节越多（64 字节的节点就是 256 GiB）。

代价也和下标一样，落在每走一步上：解码是一次移位加一次加法。移 0–3 位时（乘 1、2、4、8），x86 的寻址方式能把这一步和读合成一条指令，和下标版一样约 5 个周期；移 4 位就要先单独移一次，多约 1 个周期。换来的是节点里每个指针从 8 字节变 4 字节。订单簿、侵入式链表这种一个节点里有好几个指针的结构，每个指针都省一半，节点能小一截，一条缓存行装得更多。JVM 的 compressed oops 就是这么做的：32 位编码、按 8 字节对齐移 3 位，管 32 GB 的堆。

源 :179 的 `PtrCompressor` 有一个实测会出错的地方：它把空指针编成 0（源 :280），而池子里的**第一个对象**偏移也是 0。指针编成了小整数，“没有”和“第一个”就撞在一起：实测压缩 `&pool[0]` 再解压，得到的是 `nullptr`（源 :318）。改法是把 0 留给空指针，其余编码在原来的基础上加 1（验证程序里的 `Compressed32`；解码里的 $-1$ 可以提前并进基址，写成 $\text{基址} - 2^s$），或者另找一个值（比如 `UINT32_MAX`）表示空。另外两条要守住：池子不能超过编码能表示的范围；对象地址必须真的按 $2^s$ 对齐，否则移掉的低位就丢了。

## 4. 复合索引：几个 ID 拼成一个 64 位整数

持仓、风控这类记录，常要按几个 ID 一起查。几个字段分开存，比较要比好几次，哈希要把几个值揉在一起。把客户 ID（32 位）、会员 ID（12 位）、合约 ID（20 位）拼成一个 `uint64_t`，就能当一个整数做哈希表的键、排序、一条指令比较。源 :157 的拼法有一个坑：

```cpp
struct CompositeIndex {
    uint64_t client : 32;
    uint64_t member : 12;
    uint64_t contract : 20;
};
uint64_t encode(CompositeIndex idx) {
    return uint64_t(idx.client) | (uint64_t(idx.member) << 32) | (uint64_t(idx.contract) << 44);
}
```

源里写的是 `idx.member << 32`。12 位的位域在运算前会先**提升成 `int`**（`int` 装得下它的所有值），对 32 位的 `int` 左移 32 位是未定义行为。实测 GCC 13 给出 `-Wshift-count-overflow` 警告，结果里 `member`、`contract` 全丢了，只剩 `client`；Clang 18 干脆返回 0。上面已按实测改正：先转成 `uint64_t` 再移位。另外，位域在内存里怎么排是实现定义的，所以要稳定的编码，就像 `encode` 这样显式移位，不要直接把结构体按字节当整数用。

## 5. 大块写和写设备

### 5.1 Non-temporal store：不读回、不进缓存

[11补 轮 2 §3](11-补-内存层级-延迟与带宽.md) 讲过机制：普通写碰到不在缓存里的行，先整条读回（RFO），之后再写回，一条行在总线上走两趟；**流式写**（`_mm256_stream_si256` 这类）在 WC 缓冲（写合并缓冲）里凑满 64 B 直接写内存，只走一趟，带宽上限最多翻倍。源 :529 的清零循环就是这个。补几条用的时候要守的规矩：

- **只用在大块、近期不再读的数据上。** 写完数据不在缓存里，马上要读就得从内存读回来。块比缓存小时，普通写反而更快。
- **地址要对齐。** `_mm256_stream_si256` 要求 32 字节对齐，不对齐直接崩溃。
- **它是弱序的。** 流式写不遵守普通写之间的先后顺序，写完数据再写“就绪”标志，别的核可能先看到标志、后看到数据。发布之前要先 `_mm_sfence()`。
- **`memset` / `memcpy` 已经会用。** glibc 在块大到和共享缓存（L3）同一个量级时，自己就切换成流式写。手写的价值在于明确控制阈值，或者在 glibc 不会用的场景里用。

### 5.2 写 PCIe / MMIO：用 8 字节整块写，别用通用 `memcpy`

网卡、FPGA 的寄存器和描述符区被映射进进程地址空间（MMIO），常设成 WC（写合并）类型。对它的每一次写，最终都变成 PCIe 总线上的写事务。通用 `memcpy` 为了处理各种长度和对齐，可能拆成 1 字节、2 字节的碎写，每一笔都可能变成一个单独的事务。源 :557 的 `copy_u64_blocks` 用对齐的 8 字节写，相邻的写更容易在 WC 缓冲里合并成更少的事务；写完要求设备一定看到时，补一条 `sfence`。目标用 `volatile` 指针，是为了不让编译器把这些写合并、重排或删掉。这一条只针对设备内存，普通内存上的 `memcpy` 已经高度优化，不要替换。（没有设备，这一条未验证。）
