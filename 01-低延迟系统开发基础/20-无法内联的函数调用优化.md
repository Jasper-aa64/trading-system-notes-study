核心句：**函数调不进去时，参数按调用约定摆：小的（标量、16 字节以内的结构体、`string_view`）按值传进寄存器，大的传 `const&`；标量传 `const&` 不但多一次存和读，还让编译器不敢把它当成不变的值。递归里的尾调用，GCC 自己会变成跳转。**

## 1. 调用约定：参数先放寄存器

函数被内联时参数怎么传都无所谓。调不进去的情况：定义在别的文件或库里、通过函数指针或虚函数调、递归、函数太大。这时按 System V 约定（Linux x86-64）：前 6 个整数或指针参数放 `rdi`、`rsi`、`rdx`、`rcx`、`r8`、`r9`，前 8 个浮点参数放 `xmm0`–`xmm7`，放不下才压栈；返回值在 `rax` / `xmm0`，大的返回值走 [#17](17-关于函数的潜在优化.md) 的隐藏地址。这是源 :47 那一节背后的机制，源里没讲。

## 2. 小的传值，大的传 `const&`

源 :51–:52 的结论对，补上机制：

- `int use_val(int x)` 里 `x` 就在 `%edi`；`int use_ref(const int& x)` 要先 `movl (%rdi), %eax` 读一次。调用方 `use_ref(a + 1)` 还得开栈、把 `a + 1` 存进栈里才有地址（`subq $16, %rsp` / `movl %edi, 12(%rsp)` / `leaq`），而 `use_val(a + 1)` 是 `addl $1, %edi` 后直接 `jmp`。
- 结构体：不超过 16 字节、能按字节拷贝的拆进两个寄存器，`struct Small { double px; int64_t qty; }` 实测从 `xmm0` 和 `rdi` 进来；24 字节的 `Big` 由调用方在栈上搭一份副本，函数从栈上读。所以 `std::string_view`、`std::span`、迭代器按值传。
- 源 :53 说向 `const int&` 传常量会建临时对象、要“重载函数适配常量参数”：直接把标量按值传就没有这个问题，不用重载。

## 3. `const&` 还会挡住优化

`void scale_ref(double* v, int n, const double& f)` 里 `f` 可能指向 `v` 的某个元素，写一次 `v[i]` 就可能改了 `f`，所以循环每轮 `mulsd (%rdx), %xmm0` 重新读；`scale_val` 里 `f` 一直在 `%xmm1`。`-O3` 下 GCC 的报告是 “loop versioned for vectorization because of possible aliasing”：先插一段重叠检查。和 [#19](19-直接操作内存二进制表示.md) 的严格别名、[#16](16-指针访存优化.md) 的 `__restrict` 是同一件事。

## 4. 递归

源 :4 说的栈开销是真的：每次调用留返回地址、保存寄存器，太深会栈溢出。但源 :36 手写的“尾递归消除”编译器自己会做：

```cpp
void preorder(Node* root) {
    if (root) {
        visit(root);
        preorder(root->left);
        preorder(root->right);   // 最后一步：尾调用
    }
}
```

GCC 16 `-O2` 实测把右子树那次调用变成了 `jne` 跳回开头，只有左子树还是 `call preorder`，而且把递归往里展开了好几层。所以手写尾递归改循环多半是在重复编译器的工作。源 :19 的迭代版用 `std::stack`，底下是 `std::deque`，会分配内存；真要去掉递归，栈用固定大小的数组。遍历树的大头往往不是调用开销，而是每一步都等下一个节点从内存回来（[#16](16-指针访存优化.md) 的指针追逐）。源 :4 说递归“破坏数据局部性”不准确：局部性差是链式结构本身造成的，迭代版走的节点一样多。
