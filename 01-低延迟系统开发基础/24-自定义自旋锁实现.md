## 轮 1 自旋锁怎么写：从 CAS 循环到 TTAS 和 PAUSE（2026-10-21）

核心句：**`std::mutex` 抢不到锁就进内核睡，一睡一醒要几 µs；临界区只有几十 ns、持锁的线程又一直在跑时，原地转比睡便宜。转的时候只读不抢（TTAS），循环里加 `pause`，抢输了退一步，等锁的核才不会把锁所在的那条缓存行抢来抢去、拖慢持锁的核。**

小目录：

1. futex：`std::mutex` 抢不到锁就去睡
2. 自旋的前提：持锁的线程一直在跑
3. 最简单的自旋锁：一个原子变量，循环 CAS
4. 读改写抢行：等的核每试一次都要把行抢过来
5. TTAS：先读，看着空了再抢
6. PAUSE：别让流水线排满对这条行的读
7. 放锁的一刻：等的核一起冲

### 1. futex：`std::mutex` 抢不到锁就去睡

改订单簿的一档、拷一份行情快照，这类临界区只有几十 ns（源 :2 说的“远短于线程上下文切换耗时”）。要不要自旋，先看不自旋的锁抢不到时做什么。源 :8–11 的对比表把 `std::mutex` 写成“用户态 CAS 抢锁，抢不到走 futex 进内核”，写成代码是三个状态的一个原子整数：0 是没锁，1 是锁着、没人等，2 是锁着、可能有人在睡。

```cpp
#include <atomic>

class SleepingMutex {  // 0 = 没锁，1 = 锁着、没人等，2 = 锁着、可能有人在睡
public:
    void lock() {
        int c = 0;
        if (state_.compare_exchange_strong(c, 1, std::memory_order_acquire)) return;  // 快路径：一次 CAS
        if (c != 2) c = state_.exchange(2, std::memory_order_acquire);
        while (c != 0) {
            state_.wait(2, std::memory_order_relaxed);  // 还是 2 就进内核睡（Linux 上是 futex）
            c = state_.exchange(2, std::memory_order_acquire);
        }
    }
    void unlock() {
        if (state_.exchange(0, std::memory_order_release) == 2)
            state_.notify_one();  // 可能有人在睡，才进内核叫醒一个
    }

private:
    std::atomic<int> state_{0};
};
```

- **没人争**：`lock()` 只做一次 CAS（compare-and-swap，比较并交换：值等于 0 才改成 1），`unlock()` 只做一次 `exchange`，都在用户态，各约 2–6 ns（博客速查 2.1）。这时它和自旋锁一样便宜。
- **抢不到**：`lock()` 先把状态改成 2（“有人要睡了”），再调 `wait`。C++20 的 `atomic::wait` 在 Linux 上落到 **futex**（fast userspace mutex）系统调用：内核核对这个整数还是 2，就把线程挂到这个地址的等待队列上，切去跑别的线程（libstdc++ 的 `bits/atomic_wait.h` 里，`int` 就是直接用 futex）。
- **放锁**：`exchange` 拿到的旧值是 2，就 `notify_one`（还是 futex）叫醒一个。被叫醒的线程要等调度器把它放回某个核，才能接着 `exchange` 去抢。`std::mutex` 底下的 glibc 互斥锁用的也是这三个状态。

这一来一回要付两次系统调用（各约 0.1–0.5 µs），外加等的线程切出去、再切回来两次线程切换（各约 1–5 µs，再算上缓存被别的线程冲掉）。等的核要是进了省电状态（#1 轮 2 的 C-state），叫醒还要更久。合起来，从放锁到等的线程真正跑起来，约 2–10 µs。临界区只有几十 ns，睡一次的钱够把临界区跑上百遍，这就是自旋锁存在的理由。

### 2. 自旋的前提：持锁的线程一直在跑

转比睡划算，是因为锁很快就会放开。这要两个条件（源 :12 的“临界区执行时间远小于线程上下文切换时间”说的是第二条）：持锁的线程一直在跑，临界区很短。有一条不成立，自旋就成了白烧 CPU。

- **调度**：持锁的线程被换下 CPU（时间片用完、被别的线程抢占、等 I/O），锁就跟着它停住，等的核干转一个时间片，毫秒级，比睡一次贵得多。等的线程和持锁的线程挤在同一个核上更糟：等的一方占着核在转，持锁的一方排不上，锁放不开，直到时间片用完。所以用户态的自旋锁总和绑核一起用：每个会碰这把锁的线程各绑一个隔离出来的核（#1 轮 1），操作系统就没有理由把持锁的线程换下去。
- **临界区里做了慢事**：写日志、`malloc`、系统调用、查数据库、等网络，要么几 µs 起步，要么可能阻塞，持锁时间跟着变长、变得没法预测，等的核一直陪着转。锁里只放改数据的那几行：要查的、要算的先在锁外做完，进锁只写结果。

两条做不到，就用会睡的 `std::mutex`，或者折中：先转一小会儿，还拿不到再睡。glibc 的自适应互斥锁（`PTHREAD_MUTEX_ADAPTIVE_NP`）就是这样，不过 `std::mutex` 默认不是这种类型。

### 3. 最简单的自旋锁：一个原子变量，循环 CAS

不睡，就是把 `SleepingMutex` 里“进内核睡”换成“再试一次”。源 :24–40 的实现一就是这样（内存序已改正：源的 `lock()` 用 `acq_rel`，release 那一半对拿锁没用）：

```cpp
#include <atomic>

class CasSpinLock {
public:
    void lock() {
        int expected = 0;
        while (!locked_.compare_exchange_weak(expected, 1, std::memory_order_acquire,
                                              std::memory_order_relaxed)) {
            expected = 0;  // 失败时 expected 被改成了当前值 1，改回 0 再试
        }
    }
    void unlock() { locked_.store(0, std::memory_order_release); }

private:
    std::atomic<int> locked_{0};
};
```

- **`compare_exchange_weak(expected, 1, …)`**：`locked_` 等于 `expected`（0）就改成 1、返回 true；不等就把当前值写进 `expected`、返回 false。所以失败后 `expected` 是 1，下一轮前要改回 0。
- **`weak` 和 `strong`**：`weak` 允许偶尔“明明相等也报失败”，ARM 上用一对独占读写实现时会这样。外面本来有循环，`weak` 就够；只判断一次、失败就走才用 `strong`。
- **内存序**（接 #5 轮 3 的配对）：成功的那次 CAS 用 **acquire**，临界区里的读写不能提到拿锁之前，才看得到上一个持锁者写的；`unlock()` 用 **release**，临界区里的读写不能拖到放锁之后。两者配对，上一个持锁者在临界区里写的，下一个持锁者一定看得到。失败的 CAS 什么也没拿到，relaxed 就行。拿锁不需要 release：它管的是拿锁之前的读写，和临界区无关。

用 `exchange` 写更短：`while (locked_.exchange(1, std::memory_order_acquire)) {}`，旧值是 0 就是自己拿到的。这才是真正的测试并设置（test-and-set，TAS）。两种写法每试一次都是一次读改写（read-modify-write，**RMW**），毛病一样。

### 4. 读改写抢行：等的核每试一次都要把行抢过来

**在硬件地图上的位置**：`locked_` 住在一条缓存行里，这条行可以在好几个核的 L1D 里各有一份副本，规矩是右边 MESI 框写的：谁要写，先让别人的副本作废（5补）。

读改写是一种写。x86 上 CAS 编成 `lock cmpxchg`，不管比较成不成功，都要先把这条行拿到本核、独占（MESI 的 M 或 E），失败时把原值写回去。ARM 上换成 `casal` 这类指令，同样是对这一条行的读改写。所以 3 个核在等锁时，每个核每转一圈都要把行从别的核那里抢过来一次，每次约 20–100 ns（速查 2.6）。这条行在等锁的核之间来回搬，一刻不停。

坏的是它挡住了持锁的核：

- 持锁的核放锁要写 `locked_`，也得先把行抢回来，排在等锁的核那一串读改写后面：锁早该放了，放锁的那次写迟迟落不下去。
- 被保护的数据要是和 `locked_` 在同一条行里，临界区每改一次数据也要抢一次，临界区本身被拖长。这个好治：给锁单独一条行（`alignas(64)`，#11 / 博客 #6）。

前一个问题要改的是等的方式。

### 5. TTAS：先读，看着空了再抢

等的核只需要知道锁放了没有，读就够了；看到放了，才值得抢。这就是先测试、再测试并设置（test-and-test-and-set，**TTAS**）：

```cpp
#include <atomic>
#include <immintrin.h>  // _mm_pause，见第 6 节

class TtasSpinLock {
public:
    void lock() {
        for (;;) {
            if (!locked_.exchange(true, std::memory_order_acquire)) return;  // 先抢一次：没人争时只有这一次读改写
            while (locked_.load(std::memory_order_relaxed)) _mm_pause();    // 抢不到就只读，看着空了再回去抢
        }
    }
    void unlock() { locked_.store(false, std::memory_order_release); }

private:
    alignas(64) std::atomic<bool> locked_{false};  // 独占一条缓存行
};
```

- **持锁期间**：等的核只做普通的读。读不需要独占，3 个核各拿一份共享副本（MESI 的 S），每次读在自己的 L1D 里命中，约 1 ns，没有消息跑出核外。持锁的核不受打扰，临界区里也没人抢行。
- **放锁时**：持锁的核写 `locked_`，发一轮失效请求，3 份副本作废。等的核下一次读不命中，各自把行读回来，看到 `false`，才回第一行去 `exchange`。
- **没人争时**：第一行一次就成功，和 `CasSpinLock` 一样快。
- **循环里的读用 relaxed**：它只判断“值得去抢了”，真正拿锁靠 `exchange` 的 acquire。

### 6. PAUSE：别让流水线排满对这条行的读

源 :349–383 讲的就是这个循环。**在硬件地图上的位置**：横跨两个框，失效请求顺着灰色虚线进 invalidate queue，撞上 ROB 里还没退休的读。

`while (locked_.load(...))` 只有两三条指令：读、比较、跳回去。乱序执行的核不会等一圈做完再开始下一圈，它按分支预测（#12 轮 1）一直猜“还要再转”，把后面几十圈的读都先发出去。ROB 里于是排着一长串对 `locked_` 的读，都还没退休（retire，按程序顺序确认结果）。

锁放开的那一刻，这一串读出了问题：

1. x86 规定读和读之间不能乱序，程序里靠后的读不能比靠前的读看到更旧的值。
2. 这些读是提前发出去的，不少早就读到了旧值 `true`。
3. 持锁核的失效请求进来，这个核没法再保证它们守着这条规矩，只好把从那里开始的指令全部扔掉、重新执行。这叫**内存序冲刷**（memory ordering machine clear），和分支猜错一样冲刷整条流水线，也是几十个周期，偏偏落在锁刚放开、最该快的时候。
4. 循环出口本身还是一次分支猜错，一共付两次。

**`pause`** 让下一圈晚一点开始，流水线里同时只有一两次读，锁放开时没有一长串要扔，这次冲刷就省了。另外两个好处：转得慢了，功耗降下来；开着超线程（SMT）时，兄弟线程能用上执行资源（#1 轮 2）。

一条 `pause` 停多久，各代差很多，约 10–150 个周期：Intel 从 Skylake 起，从约 10 个周期拉长到约 140 个周期。所以“转 1000 次就去睡”这种按次数定的预算，换一颗 CPU 时间可能差 10 倍，要限时就按时间算。ARM 上没有 `pause`：`yield` 是给多线程核的提示，在很多核上等于空操作，有的库改用 `isb` 拖一小段时间；真要在等的时候省电，用 `wfe` 让核睡到这条行被别人写（轮 2，源 :385）。可移植的写法：

```cpp
#if defined(__x86_64__) || defined(__i386__)
#include <immintrin.h>
inline void cpu_relax() { _mm_pause(); }
#elif defined(__aarch64__)
inline void cpu_relax() { asm volatile("yield" ::: "memory"); }
#else
inline void cpu_relax() {}
#endif
```

别拿 `std::this_thread::yield()` 代替它：它在 Linux 上是 `sched_yield` 系统调用，每次约 0.1–0.5 µs；核上有别的线程能跑时还会把核让出去，等于自己把自己换下了 CPU。

### 7. 放锁的一刻：等的核一起冲

TTAS 让持锁期间安静了，放锁那一刻还是乱的。锁放开后，3 个等的核都读到 `false`，几乎同时回第一行 `exchange`。只有第一个成功，另外 2 个失败，可每次 `exchange` 都要把行抢过来，失败的也一样。等的核越多，这一阵读改写越长；新主人的临界区要是很短，它放锁的那次写就得排在这一串后面。所以每次交接的时间大约随等锁的核数 $N$ 线性增长：

$$t_{\text{交接}} \approx N \times t_{\text{搬行}}, \qquad t_{\text{搬行}} \approx 20\text{–}100\ \text{ns}$$

4 个核在等，一次交接约 80–400 ns，比临界区本身还长。源 :105 说的“高缓存争用”是这一节和第 4 节合起来的账。

一个办法是抢输了先退一步：

```cpp
#include <algorithm>
#include <atomic>

class BackoffSpinLock {
public:
    void lock() {
        for (int backoff = 1;; backoff = std::min(backoff * 2, kMaxBackoff)) {
            if (!locked_.exchange(true, std::memory_order_acquire)) return;
            for (int i = 0; i < backoff; ++i) cpu_relax();  // 抢输了：先歇一会儿，再去看（cpu_relax 见第 6 节）
            while (locked_.load(std::memory_order_relaxed)) cpu_relax();
        }
    }
    void unlock() { locked_.store(false, std::memory_order_release); }

private:
    static constexpr int kMaxBackoff = 64;
    alignas(64) std::atomic<bool> locked_{false};
};
```

- **指数退避**：每输一次，下次多歇一倍，各个核回来的时间错开，同时冲的少了。实际实现还给歇的长度加一点随机，免得几个核步调一致又撞上。
- **代价**：锁放开时可能大家都在歇，锁空着没人拿。
- **上限按时间想**：64 次 `pause`，在 `pause` 约 10 个周期的机器上约 0.2 µs，约 140 个周期的机器上约 3 µs，差十几倍。

等的核一多，退避也只是缓解。根本的办法是每个等的核在自己的那条行上转、按先来后到交接，放锁只惊动下一个，这是轮 2 的排队锁（票据锁、MCS 锁）。不过在交易系统里，一把锁经常有好几个核在抢，本身就说明设计该改了：改成只有一个线程写，别的线程把要改的东西通过队列交给它（#9、#10），比把锁写得再好都管用。

> 〔验证〕文中 5 段代码（和博客 #16 逐字一致）合成一个文件，GCC 16.2.0（MinGW-w64）`-std=c++20 -O2 -Wall -Wextra -pthread` 零警告；8 个线程各加 20 万次，四把锁的计数都是 1600000。这是正确性检查，不是计时。`cpu_relax` 的 ARM 分支没在 ARM 上编译过。程序：[24-spinlock-check.cpp](24-spinlock-check.cpp)。

### 轮 1 小结

- `std::mutex` 没人争时一次 CAS，和自旋锁一样便宜；抢不到就 futex 进内核睡，从放锁到等的线程跑起来约 2–10 µs。
- 自旋的前提：持锁的线程一直在跑（绑在隔离核上），临界区短、里面不做慢事。做不到就睡，或先转一会儿再睡。
- CAS 循环每试一次都是读改写，要独占锁所在的行，行在等的核之间来回搬，放锁的写也得排队。
- TTAS 先读后抢，持锁期间等的核各读各的共享副本；`pause` 免掉锁放开时的内存序冲刷，还省电、让 SMT 兄弟线程干活；放锁时的一窝蜂用指数退避缓解。

// CasSpinLock（第 3 节）
int expected = 0;
while (!locked_.compare_exchange_weak(expected, 1, std::memory_order_acquire,

    expected = 0;

// TtasSpinLock（第 5 节）

持锁的线程正在跑一个 50 ns 的临界区，另外 3 个核在等。这 50 ns 里，两种写法下，等的核各在对 `locked_` 所在的缓存行做什么？为什么 `CasSpinLock` 的持锁线程放锁时会慢？

## 与其他主题的连接

- **#5 内存模型**：轮 3 的 release / acquire 配对就是第 3 节的内存序；轮 4 的伪共享和 `alignas` 是第 4 节锁要独占一行的原因。
- **5补 MESI**：读改写要 M / E、读拿 S 副本、放锁发一轮失效，第 4、5 节整节都是它的应用。
- **#1 绑核与隔离**：第 2 节的前提；轮 2 的 SMT 和 C-state 分别接第 6 节的兄弟线程和第 1 节的叫醒更久。
- **#2 实时线程优先级**：持锁的线程被抢占是第 2 节的第一种坏法。实时优先级下更糟：高优先级的线程和低优先级的持锁线程在同一个核上转，持锁的一方永远排不上，锁永远放不开，这是自旋锁版的优先级反转。
- **#12 分支预测**：第 6 节循环出口的那次猜错。
- **#9 / #10 队列**：第 7 节结尾，单写者加队列是避开锁争用的正路。
- **#23 双数组、seqlock**：读多写少时不用锁的另一条路，轮 2 讲读写锁时接回。
- **轮 2**：票据锁、MCS 锁、读写锁、`umonitor` / `umwait` 和 `wfe`。之后是 #30 wait-free（自旋、让出、睡眠怎么选）。
